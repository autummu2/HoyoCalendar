## 1. 已完成的功能

### 1.1 采集与分类

- 米游社公告栏 `fetch_post_list(page_size=30)` + B站官方账号动态 `fetch_dynamics(limit=80)`
- **只按标题分类，不看正文**（正文关键词命中容易误杀）：卡池 / 大月卡 / 高难 / 活动各走一个
  `find_*`，剩下的按负向词丢弃（[RULES.md](RULES.md) §二）
- 卡池用**精确特征**排除（`祈愿` **且** `概率`；或 `溯光祈愿` / `集录祈愿`），不是宽泛的
  `祈愿` 二字——后者会误杀 `「巡历雪境，凝铸锋锐」…常驻祈愿5星角色` 这类活动

### 1.2 正文解析与日期口径

- **游戏日**口径：结束时刻 `03:59` → 日期减一天；**其余时刻一律照抄不减**（卡池的
  `17:59` / `14:59`、活动的 `14:59` / `5:59`）；版本更新维护 `06:00` 记单日
  （[RULES.md](RULES.md) §4.1）
- 米游社 / B站两种时间格式都支持；`版本更新后 ~ Y` 与 `版本期间持续开放` 用
  `resolve_version_starts` / `resolve_version_period` 补起点或补整段
- **B站侧起点可能为空**：时段写成 `7.1版本更新后 ~ Y`（只有一个日期）时 start 留空，
  由 `resolve_version_starts` 补——`merge_activities` 两头都有值才覆盖米游社的推断值
  （2026-09-24 修，见 §4 的开发记录）
- `永久开放` 的条目不进日历

### 1.3 周期性推理（原神特有）

原神**没有「总纲」**——米游社没有一份含本版全部活动与下版本日期的公告。
所以 `genshin/inference.py` 用纯函数补出四类事件的日期：

- **版本更新**：固定周三、周期 **42 天**，锚点 `extract_version_anchor` 从数据文件推导，
  **不硬编码**（延期或跳号只需人工改数据文件里那一条）
- **前瞻直播**：版本更新前 **11 天**
- **深境螺旋**：每月 16 号 ~ 次月 15 号；**幻想真境剧诗**：每月 1 号 ~ 月末
- 版本号是朴素 `+0.1` **预测** → 打 `待确认版本` 标签，前瞻 / 维护预告到了再校正

### 1.4 卡池日期：先推断、后校验

米游社卡池公告正文是图片，读不到日期，所以**两级处理**：先 `infer_banner_dates` 按版本节奏
推（锚点 = 距公告发布日**最近**的版本更新日；`[T, T+20]` / `[T+20, T+41]`），再用 B站总览
公告的 `〓祈愿时间〓` 覆盖（权威）。特殊祈愿的 B站动态还能反向纠正一个误判：发布日恰是版本
更新日时会被推成下半，而动态明写「版本更新后」说明是上半。

### 1.5 预筛：正文抓取 20 次 → 2 次

`_needs_body` 用 `keys.find_duplicate` + `keys.likely_recorded` 判断「这条已落盘了吗」，
已落盘的**只跳过抓正文、不从列表里剪掉**（剪掉会连带丢掉卡池与版本大活动的校准来源），
并打 `_body_skipped` 标记以免日期闸把它误报成缺口。
实测 **20 → 2 次**（1 条对不上键的版本大活动 + 1 次维护预告）。三个设计要点见
[RULES.md](RULES.md) §4.3。

### 1.6 身份与去重

主键 `common/keys.event_key`（卡池 / 版本大活动 / 大月卡按完整标题；常规活动 / 登录福利 /
网页活动按「标题 + 开始日期」；幽境危战按公告 `post_id`；版本更新 / 前瞻直播按版本号；
深境螺旋 / 幻想真境剧诗按「标题 + 开始日期」），两条兜底（版本类 ±7 天、活动类同名 ±7 天），
`id` 与主键无关且**永不改变**（前端拿它做 React key 与「已完成」追踪）。
`apply_events` **只新增、绝不改已有条目**。

### 1.7 订正与校准

两者是**两条互不干涉的通道**，是整套自动化鲁棒性的基础：

- **订正** `correct_from_candidates`：用本轮候选改已有条目的**类型**（活动公告在预筛时还
  没有类型），按标题匹配、不动日期与 id
- **校准** `calibrate`：用权威来源核对**值**（`title` / `start_date` / `end_date`），
  一致或改正后打 `calibrated` 标记，**只改不增**
- 权威来源：卡池 ← B站总览 / 特殊祈愿动态；版本大活动 ← B站活动动态；前瞻直播 ← B站前瞻
  公告；版本更新 ← 米游社维护预告。常规活动 / 大月卡 / 幽境危战 / 深境螺旋 / 幻想真境剧诗
  **不校准**（没有可靠的第二来源）
- 30 天窗口 + 只在拿到依据时才打标记 + 顺带摘掉「待确认 / 待确认版本」标签

### 1.8 颜色

按公告封面图主色取浅色（饱和度 ≤ 0.7、亮度 ~0.84），黑字可读；推理性事件（高难 / 版本
更新 / 前瞻直播）用固定色。

### 1.9 日志与风控应对

`logs/YYYY-MM-DD.log`：每轮打「正文抓取：成功 N / 失败 N（其中风控 1034: N）/ 跳过正文 M」，
**判断本轮是否可信先看这一行**；风控时表现为「0 新增」的**假阴性**，日志能区分。缺日期的
条目在日期闸处逐个 `x` 报出。详见 [RULES.md](RULES.md) §4.6。

## 4. 开发记录

按日期倒序。每条记：**起因 / 改了什么 / 实测 / 经验**。

### 2026-09-24 — B站日期口径修正 + 一轮实盘的 3 条数据订正

**起因**：7.1 的公告（9/22~9/23 发）跑一轮实盘，新增 3 条。其中
`「绮衣珍赏·晴暖」` 落成 `2026-11-04 ~ 2026-11-03`——**起晚于止**。

**改了什么**：

- [common/bilibili.py](../common/bilibili.py) 的 `parse_activity_time` 两处：
  1. 段里**只有一个日期**（起点写作版本代称，`7.1版本更新后~2026/11/04 5:59`）时
     `start` 留空，交给 `resolve_version_starts` 补版本更新日——旧实现拿那个唯一日期
     同时当起止；
  2. `end` **只有时刻是 `03:59` 才减一天**，其余照抄——旧实现不看时刻、一律减一天。
- `data/events/genshin-impact.yaml` **手工订正 3 条**（订正原因见下「经验」）：
  `「绮衣珍赏·晴暖」` → `2026-09-23 ~ 2026-11-04`；`「巡历雪境，凝铸锋锐」`、
  `「桌上剧团·冒险的前夜会」` → `end_date` 由 `2026-11-02` 改 `2026-11-03`。
- 负向词补 `装扮上架`（[RULES.md](RULES.md) §2.1）：姊妹篇 `「奇域秘藏·暄霁霄练」奇偶装扮`
  **上新**早在名单里，`「奇域秘藏·幻夜游烛」奇偶装扮`**上架**漏网，每轮白抓一次正文。

**实测**：把 7 条 B站活动动态的 `〓活动时间〓` 逐条过新旧解析器，**影响面正好 3 条**
（上面那三条），其余 4 条（多阶段的两条、`盛材移涌`、`禁界拟想阵地战`）完全不变；
无时刻的时段维持旧行为（减一天）。修正后重跑一轮：0 新增，候选与订正后的数据文件不再打架。

**经验**：

- **同一个口径写成两份实现，一定会分叉**。米游社侧 `extractor._parse_time_segment` 里写的是
  「`03:59` 减一天、其余照抄」，B站侧 `parse_activity_time` 却一律减一天；而
  `merge_activities` 让 **B站优先**，于是错的那一份赢了——米游社正文其实已经算对
  （`5:59` 照抄 → `11-04`，起点由 `resolve_version_starts` 补 `09-23`），结论被覆盖掉。
  现在两边同口径，但**仍是两份实现**，下次改要一起改。
- **「起晚于止」这种不可能值本该自动报出来**：日期闸只查「日期有没有」，不查「合不合理」。
  这次是人工扫日志才发现的（`+ 「绮衣珍赏·晴暖」 2026-11-04~2026-11-03`）。
- **写错的行自己回不来**：`apply_events` 只新增，`calibrate` 只覆盖卡池/版本大活动/前瞻/
  版本更新/高难 5 类——常规活动一旦落错就永久留在数据文件里。所以这里必须手工订正，
  光改代码没用。

| 8 | 点 `source_url` 确认 `/sr/` 路径 | ✅ 打开即星铁 4.5 版本更新说明 |

**经验**：**「行为不变」的重构要用 md5 证明，不能用「我看着没改逻辑」证明**。搬迁动了
`common/` 全部模块的 import 与路径（`PROJECT_ROOT` 从 `parent.parent.parent` 改成
`parents[3]`、产物路径改绝对），第 1 项是唯一能说明「确实没变」的运行时证据。

第 5 项那声 ⚠️ 也值一条经验：**「幂等」在跨阶段落盘的管线里不是字节级概念**。
`calibrate` 与 `apply_events` 在同一次运行里前后脚，新条目当轮来不及被校准，标记滞后一轮才
补上。所以验收口径写「第二轮 0 新增」而不是「文件不变」，**第三轮**才是真空跑。

### 2026-09-21 — 身份改造 + 待确认标签统一

**起因**：两个都属「静默出错」——不报错，但结果不对。

**改了什么**：

- 活动类主键从 `(类型, 完整标题)` 改为 **(完整标题, 开始日期)**。原因是活动日期会被校准
  改写（`版本更新后 ~ Y`、B站补日期），而类型要等 B站动态才定；把会变的东西当身份，校准
  一改就变成「新活动」重复落盘
- 加**活动类同名 ±7 天兜底**（`DATE_TOLERANCE_DAYS = 7`）：日期进了身份，被订正后主键会失配，
  兜底把它认回来
- `待确认` / `待确认版本` 两个标签收进 `common/keys.py` 统一定义。此前**产出侧写「待确认」、
  清除侧只认「待确认版本」**，标签永远摘不掉

**实测**：预筛的旧做法是给候选**预填「常规活动」**凑主键，活动公告在主键上对不上，版本大
活动因此**每轮都被多抓一次**（实测 `「险境征者竞锋大赛」`）；改用 `keys.likely_recorded`
（按「标题 + 同名条目开始日期不早于公告发布日」认，覆盖 `ANNOUNCEMENT_ACTIVITY_TYPES`）
之后不再多抓。

**经验**：**标签的字面量必须只有一处定义**。两边各写一遍字符串时，编译器不会提示「这俩本来
应该是同一个」，而症状是「标签摘不掉」这种不报错、只表现为数据慢慢变脏的问题。

**身份不能包含会被自动化改写的字段**——这是那次改造的真正教训。判断标准：字段在条目生命周期
里会不会被管道改写？会，就不该进主键。

## 6. 实现决策

| 决策 | 为什么 |
|---|---|
| **不要状态文件** | `genshin-impact.yaml` 自己就是状态：预筛（跳过谁）、推理（版本锚点）、订正、校准都从它读。少一个文件就少一处与人工编辑冲突的可能 |
| **新增只增不改、校准只改不增** | 两条通道职责正交，判定都走同一个 `keys.event_key`。这样自动化**永远不会覆盖人工编辑**，人工也不必担心自己的改动被管道吃掉 |
| **预筛复用 `apply_events` 的同名去重** | 它跳过的，`apply_events` 本来也会跳过，所以预筛**不可能比现有去重更激进**——不会因为省请求数而丢新活动 |
| **订正按标题匹配，不按主键** | 要订正的恰恰**包含类型本身**，主键此时还是错的 |
| **护栏：候选是默认类型时不写回** | 类型只有往「版本大活动」一个方向订正；反向写回会把已订正的条目打回默认值 |
| **取色排在最后** | 取色要为每条条目下载封面图；排在日期闸之前，会给马上就要被丢弃的条目白下图片 |

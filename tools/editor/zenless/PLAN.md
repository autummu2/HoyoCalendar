# 绝区零自动化维护 — 方案

> **状态**：**已实施**（2026-09-21）。`rules/parse/inference/pipeline/selftest` 已落地，
> 离线自检 152 项、真实跑通一轮。本文依据**一次真实抓取**（2026-09-21，40 条公告 + 12 篇正文）
> 写成，落地过程中的两处修正见 §5 已定 6 与 §7。
> 代码中的常量以 `rules.py` 为准，本文件与它若有出入，以 `rules.py` 为准。

## 1. Context

原神（`genshin/`）与星铁（`starrail/`）两条管线已跑通。绝区零要做第三条。

**结论：绝区零是三条线里最容易的一条**，因为它的**停服更新公告是一份完整的版本总纲**：
版本更新日、版本结束日、该版本全部活动的起止、高难期数，全在一篇里。星铁的总纲
（版本更新说明）给的东西类似；绝区零的总纲给得更多——**连每个活动的日期都直接写着**。

原先的草稿以为「绝区零版本终点要按 42 天推、高难日期要纯猜」，**实测推翻了**（见 §2.4、§2.6）。

**目标**：与另两条管线同等程度——跑一次，新增版本更新/卡池/活动/大月卡/前瞻/高难自动落盘，
已有条目按权威来源校准。

## 2. 实测的公告结构

### 2.1 来源与它们各自给出什么

米游社公告列表（`GIDS_MAP["zenless-zone-zero"] = 8`）40 条覆盖 2026-07-27 ~ 09-21（56 天）。

| 公告标题形如 | 给出什么 |
|---|---|
| `X.Y版本「NAME」更新公告` | **总纲**：`【更新开始时间】`、**`X.Y版本结束时间为 YYYY/MM/DD HH:MM，该版本共持续N天`**、`六、全新活动`（每个活动的 `活动时间：`）、`▶危局强袭战`/`▶式舆防卫战`（各 3 期，**只有敌人、没有日期**） |
| `X.Y版本「NAME」预下载开启&更新通知` | 只给 `【预下载时间】`；版本终点只说「截止至X.Y版本结束前」**不给日期** |
| `X.Y版本限时频段（上期/下期）` | `本期代理人与音擎调频活动时间为：A ~ B` + 各频段的 S 级代理人与音擎 |
| `X.Y版本「丽都城募」说明` | `【活动时间】`（大月卡） |
| `「X」活动说明` | `【活动时间】`、`【活动奖励】`、`【参与条件】`、`【活动说明】` |
| B站官方动态（uid **1636034895**） | 前瞻预告里的 `将于8月28日 19:30正式开启` |

需要**排除**的（标题命中即跳过，否则每轮白抓正文又永远落不了盘）：

- `X.Y版本「商城」上新说明`、`X.Y版本已知问题及游戏优化说明`
- `《云·绝区零》X.Y版本更新说明`（云游戏，不是本体；注意它和本体的 **`X.Y版本「NAME」更新公告`** 只差几个字）
- `《绝区零》PC端视觉体验升级功能使用FAQ`、`新剧情：主线第…`

> 实测 B站动态正文与米游社公告**逐字相同**。所以 B站**只用来拿前瞻**，其余一律走米游社。

### 2.2 总纲（停服更新公告）的段结构

实测 `77014071`（3.1）、`78055591`（3.2）两篇，结构一致：

```
【更新开始时间】2026/09/09 06:00 预计5个小时完成。
【补偿说明】 … ※领取时间截至3.2版本结束前，3.2版本结束时间为 2026/10/21 06:00 ，该版本共持续42天…
【版本全新内容】
  一、全新代理人   • S级代理人[克拉蕾(电·锋御)] 可通过「红月初升」频段调频获得。
  二、全新音擎     • S级音擎[猩红渴望(锋御)] …
  三、全新剧情 / 四、全新地区 / 五、全新时装
  六、全新活动
     • 惊喜放映企划
       累计签到得「妄想天使」时装自选、头像、菲林等奖励。
       活动时间：2026/09/23 10:00 ~ 2026/10/20 03:59
       参与条件：绳网等级≥5级…
     • 天使应援大作战 … 活动时间：3.2版本更新后 ~ 2026/11/30 03:59 …
     • 潜能预演·烈火重锤 … 活动时间：3.2版本更新后 ~ 3.2版本结束 …
  七、其他更新内容 ▶新增&调整内容 … ▶危局强袭战 … ▶式舆防卫战 …
```

**`X、全新活动` 段的每个活动都带 `活动时间：`**，一行起止，格式与单独公告的
`【活动时间】` 一致。3.2 总纲列了 11 个活动，其中 4 个（跛脚乌鸦奇探录、锵锵！球仔成长日记、
数据悬赏-实战模拟、「嗯呢」从天降）**单独公告还没发**——总纲能提前拿到。

> ⚠️ 段号**每版不同**（3.1 是 `七、全新活动`，3.2 是 `六、全新活动`），任何按段号定位的
> 写法都会过期。本管线干脆不解析这一段（理由见 §5 已定 6），此处仅作结构说明。
>
> ⚠️ **总纲里的活动名与单独公告的标题写法不同**（实测两处）：
> 总纲写 `• 「嗯呢」大派送！`、`• 「弹球勇者」哐哐当！`，而单独公告的标题是
> `「『嗯呢』大派送！」活动说明`、`「『弹球勇者』哐哐当！」活动说明`。
> 即**外层再包一层「」时，内层的「」要改写成『』**（中文引号的嵌套惯例）。
> 数据文件用的是后一种。本管线不依赖这个转换：标题一律取自公告 subject 的最外层「」，
> 嵌套照抄（`RE_OUTER_NAME` 的字符类排除「」，所以内层的『』原样保留）。

### 2.3 日期口径（实测确认）

与原神/星铁**同一条规则**：结束时刻 ≤ 06:00（游戏日 04:00 边界）→ 结束日减一天；
白天时段（11:59 / 14:59 / 20:30）→ 照抄。

**但现有手工数据有 6 条没减**，且自相矛盾——同样是 `09/07 03:59` 结束，
`极危通缉与悠游假期` 记成 09-06、`咔滋酥脆出餐计划` 记成 09-07。所以这不是
两套口径，是录入遗漏。数据文件里 11 条「减了」、6 条「没减」，见 §4 订正清单。

| 公告原文 | 推出 | 数据文件 |
|---|---|---|
| `2026/08/24 10:00 ~ 2026/09/07 03:59`（极危通缉） | 08-24 ~ **09-06** | 09-06 ✓ |
| `2026/08/07 10:00 ~ 2026/08/24 03:59`（咔嚓！焦点对决！） | 08-07 ~ **08-23** | 08-23 ✓ |
| `2026/08/28 10:00 ~ 2026/09/14 03:59`（叮咚！见习邮差派件中） | 08-28 ~ **09-13** | 09-13 ✓ |
| `2026/09/10 10:00 ~ 2026/10/19 03:59`（弹球勇者） | 09-10 ~ **10-18** | 10-18 ✓ |
| `2026/09/16 10:00 ~ 2026/10/05 03:59`（虚境逐影争锋） | 09-16 ~ **10-04** | 10-04 ✓ |
| `2026/09/07 03:59` 结尾（恰浪花逐夏而至） | 09-06 | 09-07 ✗ |
| `2026/11/30 03:59` 结尾（天使应援大作战） | 11-29 | 11-30 ✗ |
| `2026/09/08 03:59` 结尾（「嗯呢」大派送！） | 09-07 | 09-08 ✗ |
| `2026/09/07 03:59` 结尾（咔滋酥脆出餐计划） | 09-06 | 09-07 ✗ |
| `2026/10/20 03:59` 结尾（惊喜放映企划） | 10-19 | 10-18 ✗ |
| `~ 3.1版本结束` = 09/09 06:00（法厄同年度大揭秘） | 09-08 | 09-09 ✗ |
| `2026/09/30 11:59`（3.2 卡池上期，白天时段） | **09-30** | 09-30 ✓ |

**大月卡结束日 ≠ 版本终点**（与星铁同一条）：丽都城募
`3.2版本更新后 ~ 2026/10/19 03:59` → **10-18**，而 3.2 最后一天是 **10-20**。
一律以丽都城募自己的公告为准。

### 2.4 版本期间 —— 公告直接写着，不用推

**两篇停服更新公告都有这句**：

```
※领取时间截至3.2版本结束前，3.2版本结束时间为 2026/10/21 06:00 ，该版本共持续42天，请绳匠注意。
※领取时间截至3.1版本结束前，3.1版本结束时间为 2026/09/09 06:00 ，该版本共持续42天，请绳匠注意。
```

所以：

- **版本更新日** = `【更新开始时间】`（T）；预下载公告的 `【预下载时间】` 是 T−2，作提前量/校验
- **版本终点（最后一天）** = `版本结束时间` 按 §2.3 口径减一天
  （3.1 → 09-08，3.2 → 10-20；`07-29..09-08` 与 `09-09..10-20` 都正好 42 天，与公告自称的「共持续42天」吻合）
- **周期 42 天**是公告自己写的，两个样本一致，**不需要按周期外推**
- 于是 `X.Y版本更新后 ~ X.Y版本结束` 这类相对时间**当场可解**
  （法厄同 → `07-29 ~ 09-08`、潜能预演·烈火重锤 → `09-09 ~ 10-20`）

### 2.5 卡池

`X.Y版本限时频段（上期）` 正文开头一句：

```
本期代理人与音擎调频活动时间为： 3.2版本更新后 ~ 2026/09/30 11:59 ，包含如下内容：
「红月初升」调频活动
  活动期间，限定S级代理人 [克拉蕾(电·锋御)] 以及默认A级代理人 …
「猩红渴望」调频活动
  活动期间，限定S级音擎 [猩红渴望(锋御)] 以及默认A级音擎 …
```

**一条公告含多个「调频活动」，数据文件只落一条。** 命名是
**`调频活动-` + 该公告里全部「限定S级代理人」的名字（按文中顺序 `/` 连接），音擎不列**：

| 公告 | 数据文件标题 |
|---|---|
| 3.2 上期（4 个频段，代理人只有克拉蕾、南宫羽） | `调频活动-克拉蕾/南宫羽` |
| 3.1 下期（含「独家重映」自选池，可选 3 名代理人全列） | `调频活动-希格莉德/琉音/浮波柚叶/浅羽悠真` |

代理人与音擎在文本里**可无损区分**：代理人 `[名字(属性·特性)]`（带 `·`），
音擎 `[名字(特性)]`（不带）。

⚠️ 这个标题格式是**手工约定**（官方是「红月初升」这种频段名）。已确认沿用（§5 已定 1），
意味着解析器必须**一字不差**复现，否则下一轮会把 4 条卡池当新活动重复插入。

⚠️ **3.1 上期的标题是 `3.1版本限时频段`，没有「（上期）」后缀**（3.2 才有）。
分类正则必须容忍缺省。

### 2.6 高难挑战（危局强袭战 / 式舆防卫战）

总纲的 `▶危局强袭战` / `▶式舆防卫战` 段各列 **第一期/第二期/第三期**（含敌人与增益），
**完全没有日期**。

数据文件里的日期排出来：

```
危局强袭战   07-29(周三)  08-14(周五 +16)  08-28(周五 +14)  09-11(周五 +14)
式舆防卫战              08-07(周五)       08-21(周五 +14)  09-04(周五 +14)  09-18(周五 +14)
```

**推出的网格**：版本更新日之后的**第一个周五**是首期危局，此后每周交替
（式舆 = 危局 + 7），各 3 期（3 期 × 每周交替 = 6 周 = 42 天 = 一个版本 ✓）。
每期的结束日 = **下一期同类开始日 − 1**。

验证（16 个手工日期里 15 个吻合）：

| 版本 | 更新日 | 首期危局 | 推出 | 数据文件 |
|---|---|---|---|---|
| 3.1 | 07-29 周三 | 07-31 周五 | 危局 07-31/08-14/08-28，式舆 08-07/08-21/09-04 | 危局 **07-29**/08-14/08-28，式舆 08-07/**08-21**/09-04 |
| 3.2 | 09-09 周三 | 09-11 周五 | 危局 09-11/09-25/10-09，式舆 09-18/10-02/10-16 | 危局 09-11，式舆 09-18 |

两处不符：

- **危局 07-29**（周三，恰是 3.1 更新当天）——比网格早 2 天。唯一解释是版本首期
  特例或录入误差，无从判定（已定：不改，见 §5 已定 5）。
- **式舆 0807 的结束日 08-21**——下一期 0821 也是 08-21，重叠一天。按「下期同类 − 1」应为 08-20。

> 只要管线**只为「当前版本」推期次**（3.2 的公告推 3.2 的 6 期），3.1 那个 07-29
> 就已经在窗口之外，永远不会与推出的 07-31 撞车——不需要任何例外名单。

### 2.7 三种活动类型的判据（实测）

| 类型 | 判据 | 实测样本 |
|---|---|---|
| **版本大活动** | 段标记含 **`【活动常驻说明】`** 或 **`【丽都纪事】`** | 恰浪花逐夏而至 有 → 版本大活动 ✓；天使应援大作战、法厄同、玛瑟尔周年馈礼、极危通缉、咔嚓、实战特训、深度巡防 **全无** → 常规活动 ✓ |
| **网页活动** | 正文里有**非图床外链**（`href="https://mhyurl.cn/…"`，正文表现为 `>>>点击前往参与活动<<<`） | 法厄同年度大揭秘 有（`mhyurl.cn/8PFqQ2wRa`）✓；另外 7 篇只有 `upload-bbs.miyoushe.com` 图床链接 ✓ |
| 常规活动 | 以上都不是 | — |

**不是每个版本都有版本大活动**——3.2 就没有，所以现有数据里 3.1 的标「版本大活动」、
3.2 的标「常规活动」**是对的**（草稿里说「两处口径不一致」是错的）。

## 3. 实施方案

### 3.1 模块划分

与另两条**并列**的第三条线，复用 `common/`：

```
tools/editor/zenless/
├── rules.py       常量：gid、抓取参数、排除词、段标记、颜色、标题格式
├── parse.py       纯函数解析层（总纲 / 活动正文 / 卡池正文 / 大月卡），不联网不读写文件
├── inference.py   高难网格；相对时间（`X.Y版本更新后` / `X.Y版本结束`）求解
├── pipeline.py    编排：抓取 → 预筛 → 解析 → 推理 → 校准 → 写 extracted_zzz.json
├── selftest.py    离线自检（配 fixtures/）
├── fixtures/      真实公告夹具
├── RULES.md / PLAN.md
└── extracted_zzz.json
```

### 3.2 `common/` 的改动（加法式，另两条线行为不变）

| 文件 | 改动 |
|---|---|
| `common/yaml_io.py` | `GAME_URL_PATH` 加 `"zenless-zone-zero": "zzz"`（已核对：有效 slug 返回 200，`zzzz`/`zzzz2`/`nothinghere` 返回 404 且只有 9 字节） |
| `common/calibrate.py` | **不动**。`sources_from(..., game_name="绝区零")` 的参数已存在，直接传。`CALIBRATED_TYPES` 里已有的 5 类（卡池/版本大活动/前瞻直播/版本更新/高难挑战）够用——再加 `常规活动`/`网页活动`/`登录福利` 是**死配置**：绝区零没有独立于公告的第二个来源，那三类的日期本来就出自同一篇公告，自己校准自己没有意义 |

`keys.py` **不动**：绝区零没有星铁那种「标题每期一字不变」的周期性活动
（三倍类标题 `深度巡防-三倍赏金` / `实战特训-三倍悬赏` / `先遣赏金-区域巡防` 各不相同；
高难标题自带 MMDD 也不重复）。

### 3.3 `run()` 顺序

1. `fetch_post_list("zenless-zone-zero", page_size=40)`，按 `post_id` 去重
2. 按标题分流：停服更新公告 / 限时频段 / 丽都城募 / 活动说明；`is_activity` 用
   **`活动说明` 后缀**当判据（不是排除名单，名单会过期）
3. **总纲（停服更新公告）**先跑，产出：
   - `【更新开始时间】` → 版本更新日
   - `版本结束时间为 YYYY/MM/DD HH:MM` → **下一个版本**的更新日（本版终点 = 它减一天）
   - `▶危局强袭战`/`▶式舆防卫战` 的 `第N期` 计数 → 高难期数
   - 窗口内**所有**总纲都抓：活动日期大量写成 `X.Y版本更新后` / `X.Y版本结束`，要按版本号查表
4. **活动**：标题逐字取自**各自公告的 subject**，类型与日期由其**正文**派生
   （见 §5 已定 6；条目的身份见 §5 已定 8）
5. **卡池**：`版本限时频段` 正文 → §2.5 标题 + 时间段
6. **大月卡**：`丽都城募说明` 的 `【活动时间】`
7. **高难**：按 §2.6 网格推**当前版本**的 3 期危局 + 3 期式舆
8. **前瞻**：B站 `fetch_dynamics(1636034895, limit=80)` → 复用 `common.bilibili.parse_livestream`，
   外加一道「必须带具体 `X月X日`」的闸（前瞻当天和节目本体那两条动态没有日期）
9. `_needs_body` 预筛（`keys.find_duplicate` + 活动类另用 `keys.likely_recorded`：预筛时
   活动的类型还没定，只能按**标题 + 公告发布日**认）——
   稳态请求数的主控，也是米游社风控（`retcode 1034`）的唯一有效对策
10. 校准 `calibrate(events, sources)`（权威值 = 总纲的版本更新日 + 网格推的高难期次 +
    B站前瞻）→ 日期闸 → 取色 → 写 `zenless/extracted_zzz.json`
    → 交 `apply_events.main("zenless-zone-zero", OUT_FILE)`
11. `maintain.py` 的 `GAMES` 加第三项，各自 try 住

### 3.4 请求预算

实测一轮：米游社列表 1 次 + 正文 12 次 + B站动态 2 页。总纲篇幅大（3.2 那篇 24K 字）
但**一篇顶十几篇**——预筛生效后稳态正文请求是个位数。

## 4. 数据订正清单（实测定出）

**A. 日期口径遗漏 6 条**（§2.3）

| 条目 | 现值 | 应为 | 依据 |
|---|---|---|---|

## 9. 总纲优先落地 + 订正通道（2026-09-21 已实现，见 §9.6）

### 9.1 为什么绕回原定方案

§5 已定 6 记的原方案就是「标题取总纲名 + 嵌套转换，**版本更新当天落盘整版活动**」，
落地时因为「类型在去重主键里」改成了只取公告。已定 9 把类型移出主键后那条阻碍消失，
这里把它做回来。

**收益不是省事，是提前**：总纲比活动自己的公告早得多——3.2 里「惊喜放映企划」
「先遣赏金-区域巡防」早 **12 天**，「数据悬赏-实战模拟」早 **35 天**。按公告落盘时这些
活动在日历上要等到公告发布（实测公告平均只比活动开始早 2 天，见 §7），总纲优先能让整版
活动在版本更新当天就挂上去。

### 9.2 本轮实测（复核，不靠记忆）

- 总纲活动段在 `content` 的 **`<p>` 段落**里结构干净：`• 名称` 独立一段、`活动时间：…`
  独立一段（`text` 是压平过的，段落边界没了，名字里还可能有空格——`回归丽都 羽落重逢`，
  所以必须解析 `content` 而不是 `text`）。段号每版不同（3.1 是 `七、`、3.2 是 `六、`），
  按**后缀**「全新活动」定位，且要在下一个编号段（如 3.1 的 `八、全新玩法`）处截断。
- **日期可信**：与已落盘数据逐条比对，**15 条重叠全部一致，0 条不一致**。
- 引号写法与公告不同（§2.2 已记）：总纲 `• 「嗯呢」大派送！` vs 公告 subject
  `「『嗯呢』大派送！」` → 标题按嵌套惯例转换（外层包「」，内层「」改『』）。
- 总纲**给不出**三样，只有活动自己的公告才有：**类型**、**配图**（活动段 0 张图，
  所以 `color` 只能是兜底色）、**公告全文描述**（总纲只有一两行）。

### 9.3 方案

| # | 改动 | 要点 |
|---|---|---|
| 1 | `parse.parse_version_activities(content, versions)` | 按后缀定位活动段 → 取 `• 名称` 与 `活动时间：`，日期复用现有 `resolve_period` |
| 2 | `pipeline._activities_from_notes(contents, versions)` 产出总纲候选 | 与公告候选并列进 `acts`，按身份去重留先出现的（公告那条信息更全）；`type` 落默认 `常规活动`，标 `pending: "总纲"` |
| 3 | `keys.likely_recorded`：条目带 `pending` 时不跳过 | 否则公告到了也不抓正文 → 永远学不到类型，整条路白做 |
| 4 | `keys.find_duplicate` 兜底集合放宽到 `ANNOUNCEMENT_ACTIVITY_TYPES` | 修既有 bug：类型跨轮变化（常规活动→版本大活动）时主键失配、兜底也不进 → `apply_events` **插重复**（已离线复现） |
| 5 | 新增 `calibrate.correct_from_candidates(events, candidates)` | 用本轮候选订正已有条目：候选类型有依据时写回 `type`；带 `pending` 的条目补 `description` / `color` 并清标记。**不动 id、不动日期**。做成独立函数而不是加进 `VALUE_FIELDS`——它按**标题**匹配（要订正的恰恰包含类型本身），而 `VALUE_FIELDS` 走的是主键 |
| 6 | `apply_events` 白名单加 `pending` | 否则标记写不进数据文件，下一轮就认不出哪些条目待补全 |

**标记用内部字段而不是 `tags`**：`tags` 在前端会渲染成徽章（`DayView` / `EventDetail`），
版本更新后整版活动都挂个「待确认类型」会很吵。`pending` 沿用 `calibrated` 那套
（`EventSchema` 不是 `.strict()`，前端 Zod 静默丢弃，界面无感）。

**两条护栏**：

1. 候选类型为 `常规活动` 时**不写回 type**。理由是它在三条管线里都是「没有肯定信号」的兜底值
   （原神无 B站动态时、星铁无版本期间时、绝区零无任何段标记时都落回它），不是判据。这条同时
   挡住两种坏结果：原神的降级（类型来自 B站列表，动态被翻页刷掉后候选会退回常规活动，无条件
   写回会把已确认的版本大活动改错），以及把人工标的 `登录福利` 抹成常规活动。
2. **候选自己也带 `pending` 时整条跳过**（这条是实现时才发现要加的，见 §9.6）。总纲列出的活动
   每轮都会再产出一条带标记的候选，它与待补全的条目身份相同，但**补不了**描述与配图——放它
   过去就会「假补」：标记被清掉，下一轮预筛按「已录入」跳过该活动的公告正文，描述与配图
   **再也补不上了**。缺口宁可留着（继续重抓正文），不能假补。

### 9.4 副作用（要先认下再动）

- **数据文件会新增条目**：实测 3.2 有「「嗯呢」从天降」「数据悬赏-实战模拟」、3.1 有
  「回归丽都 羽落重逢」（07-17~09-08，已结束）此前没落盘，总纲优先后会被补录。
- **`id` 会带着落盘时的类型**：早落盘是 `zzz-常规-2026-09-…`，之后类型订正为 `登录福利`
  时 id 不变（`id` 永不改变是既有规则，前端用它追踪「已完成」）→ id 与类型字面不一致。
- **总纲日期成为第一权威**：与公告冲突时不动日期（实测 15/15 一致，这条目前是空转）。
- 「回归丽都 羽落重逢」按 §5 已定 7 是 `登录福利`（正文含「邀请好友」），会一并收录。

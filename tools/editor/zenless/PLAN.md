## 1. 已完成的功能

### 1.1 五个模块落地

与另两条**并列**的第三条线，复用 `common/`：

```text
tools/editor/zenless/
├── rules.py       常量：gid、抓取参数、排除词、段标记、颜色、标题格式
├── parse.py       纯函数解析层（总纲 / 活动正文 / 卡池正文 / 大月卡），不联网不读写文件
├── inference.py   高难网格；相对时间（`X.Y版本更新后` / `X.Y版本结束`）求解
├── pipeline.py    编排：抓取 → 预筛 → 解析 → 推理 → 校准 → 写 extracted_zzz.json
├── selftest.py    离线自检（配 fixtures/）
└── fixtures/      真实公告夹具 + 一份抓取到的公告列表与 B站动态 80 条
```

离线自检 **255 项**（断言解析结果与数据文件逐字一致），`python zenless/selftest.py`。

### 1.2 总纲优先 + 订正通道（**已实盘**）

**绝区零是三条线里唯一有「总纲」并且把总纲用作主来源的**：停服更新公告的 `X、全新活动`
段列出**整版活动**（名字 + `活动时间：`），比活动自己的公告早 **12~35 天**
（实测公告发布日平均只比活动开始早 **2 天**）。所以活动**两个来源并列收**：总纲先落盘
（默认类型 + `pending: 总纲`），公告出来后再由 `correct_from_candidates` 补类型 / 描述 /
配色并清标记。两份候选按身份去重、留先出现的公告那条（信息更全）。

**已实盘**：数据文件从 **45 → 48 条**，新增的正是方案里预测的那三条——「『嗯呢』从天降」
「数据悬赏-实战模拟」「回归丽都 羽落重逢」。三条目前仍带 `pending: 总纲`（§2.3），
配色是兜底色 `#cce0f0`、没有描述，这正是设计中的中间态。

两条护栏见 [RULES.md](RULES.md) §3.6.2（候选为默认类型时不写回 type；候选自己带 `pending`
时整条跳过，不许「假补」）。

### 1.3 活动身份改造

活动类去重身份改为 **(完整标题, 开始日期)**，**不含类型**（2026-09-21，动的是共用层，
三条管线一起改）。起因是实测**活动名会跨版本重复**——「全新放送」在 3.0 与 3.2 各有一期、
同名同类型，老的 `(类型, 标题)` 会**静默跳过**新一期。
顺带解掉的：类型不再进身份 → 「先按总纲落盘、事后订正类型」不再会插重复 = §1.2 的前提。
代价：日期进了身份，被订正后主键会失配 → `find_duplicate` 加**同名 7 天兜底**认回。

### 1.4 高难期次网格

总纲的 `▶危局强袭战` / `▶式舆防卫战` 段**只有期数、没有日期**。网格：版本更新日之后第一个
周五是首期危局，此后每周交替（式舆 = 危局 + 7），各 3 期（6 周 = 42 天 = 一个版本）。
**只为当前版本推期次** → 已知例外 `危局强袭战0729` 自然落在窗口外，不需要例外名单。
实测 16 个手工日期里 **15 个吻合**。

### 1.5 正文本机缓存

`common/body_cache.py`，TTL 14 天，`_fetch` 命中就不发请求。稳态正文请求从个位数降到 **0**
（实测第二轮：成功 0 / 缓存命中 5 / 跳过 22）。缓存里连 `content`（网页活动判据要用的原始
外链）一起存。设计说明与 TTL 取 14 天的理由见 [../starrail/PLAN.md](../starrail/PLAN.md) §1.5。

### 1.6 活动四类型的派生判据

网页活动（`content` 里有非图床外链）/ 版本大活动（`【活动常驻说明】`·`【丽都纪事】`）/
登录福利（`累计登录`·`登录即可`·`邀请好友`）/ 常规活动（其余）。**三种都有判据，不建名单**；
判据与实测样本见 [RULES.md](RULES.md) §2.2。

### 1.7 版本边界由公告明写

三条线里唯一一个**不用任何外推**的：总纲写着「X.Y版本结束时间为 YYYY/MM/DD HH:MM，
该版本共持续42天」。版本更新日 = `【更新开始时间】`，本版终点 = 版本结束时间减一天，
周期 42 天也是公告自称的。预下载通知不另解析（它给的信息与总纲重合）。

### 1.8 数据订正清单已全部落盘

实测定出的 6 条日期口径遗漏 + 1 条高难网格 + 2 条类型订正 + 版本更新两条的标题 / id 统一，
**已全部改完**（清单原样保留在 §6.2 供追溯）。`3.1版本「漫长的告别」更新` 与
`《绝区零》3.2 版本「她与她的隐秘往事」停服更新` 两条标题格式已统一。

## 4. 开发记录

按日期倒序。每条记：**起因 / 改了什么 / 实测 / 经验**。

### 2026-09-24 — 一轮实盘观察：一条 `pending: 总纲` 摘不掉

**起因**：跑一轮实盘核对（今天另两条线各有新公告，绝区零没有）。

**实测**：0 新增 / 36 跳过是**对的**——米游社列表里最新的公告停在 09-21，3.2 那批
（09-07~09-21）早就落盘了。但 3 条 `pending: 总纲` 里，`「回归丽都 羽落重逢」`
（07-17~09-08）的**活动公告在抓取窗口之外**：窗口最早只到 07-27，而这类公告发在活动开始
前后（约 07-16）。订正通道永远等不到那篇公告 → `pending` 摘不掉，而且每轮仍会读一次正文
（走本机缓存，0 请求）。另两条 `「『嗯呢』从天降」`（09-30）、`「数据悬赏-实战模拟」`
（10-14）是正常的「公告还没发」。

**处置**：**仅记录，未改**。`pending` 不进前端（不在 Zod schema 里，界面无感），代价只有
每轮一次缓存读；要不要手工清掉那条标记由用户定。

**经验**：`pending` 这类「等一条还没到的东西」的标记，加的时候都要问一句**「那条东西还在
抓取窗口里吗」**——窗口每天往前挪，窗口外的就永远等不到，标记会从「待确认」变成常驻。

### 2026-09-22 — 正文按 `post_id` 本机缓存

**起因**：预筛已消掉稳态下的重复抓取，但「同一天内多次运行」仍会重复抓新条目；米游社正文
接口有风控（`retcode 1034`），请求数是唯一可控量。

**改了什么**：新增 `common/body_cache.py`（TTL **14 天**），各管线 `_fetch` 命中缓存就不发
请求。缓存里连 `content`（网页活动判据要用的原始外链）一起存——只存 `text` 的话判据会失效。

**实测**：第二轮 成功 0 / 缓存命中 5 / 跳过 22，稳态正文请求 **0**。

**经验**：**TTL 要按「内容会不会变」定，不是按「多久重跑一次」定**——公告发布后正文就冻住了，
14 天远小于公告的有效期，所以缓存不会拿到过期内容。设计细节与星铁侧的实测表见
[../starrail/PLAN.md](../starrail/PLAN.md) §1.5。

### 2026-09-22 / 2026-09-24 — 流程图偶发空白（已定位并解决）

**起因**：VSCode 里打开本文件预览，`§0.1` 那张流程图**闪一下就没了**，深色主题下看着像
一片纯黑（其实是**空的**，不是「渲染成黑色」）。

**结论**：**markdown-mermaid 预览插件与其它插件的冲突**，不是配色、不是图语法错。
当时按扩展的重画行为量过一轮（`el.innerHTML = ""` 后异步 `mermaid.render("d"+内容哈希)`，
同一 id 的两次并发渲染会拿到一张空 SVG 且不抛异常；那张图 55 节点 / 122 个 `foreignObject`，
渲染窗口 76~187ms，撞得上；小图 9~11ms 撞不上），据此把首行钉成
`%%{init: {"flowchart": {"htmlLabels": false}}}%%`，把渲染时间压到约一半。

**2026-09-24 收尾**：插件侧的问题已解决，空白不再复现。本文件**不再放流程图**——
`PLAN.md` 讲「做了什么、还差什么」，管线怎么跑该看 [RULES.md](RULES.md)；图放在那边
（每类活动一张），本文只留文字。

**经验**：**可读性优先于「不会偶发空白」**。「拆成三张」的方案被用户当场否掉是对的——
为了压一个偶发、重开预览就能恢复的渲染竞态去改文档结构，是本末倒置。
**另一条**：`PLAN.md` 与 `RULES.md` 的分工要守住——把「怎么跑」的大图放进 PLAN，
等于在历史记录里维护一份会过期的现状描述。

### 2026-09-21 — 追加一轮：白名单、取色顺序、标签统一、星铁接入

上面「总纲优先」那一轮之后的一组改动。前两条是**同一类教训**：那一轮的离线验证验的是
解析与订正**函数本身**，没有把整条 `run()` 串起来跑，于是两个「函数对、接线错」的问题
活了下来。

| # | 问题 | 症状 | 修法 |
|---|---|---|---|
| 1 | **产物白名单漏 `keys.PENDING_FIELD`** | 产物 JSON 里没有 `pending` → `apply_events` 写不进数据文件 → 下一轮预筛认不出待补全的条目 → **总纲优先整条路空转**（活动照落盘，描述与配色永远补不上）。不报错、不丢条目，纯粹静默失效 | 两个管线各加 `OUT_FIELDS` 常量（含 `keys.PENDING_FIELD`）并据此投影；两个自检各加一条白名单守卫 |
| 2 | **取色排在订正之后** | `correct_from_candidates` 补的 `color` 来自候选，而候选的 `color` 是取色那一步填的 → 订正时永远拿不到 → 总纲落盘的活动一直停在兜底色。**日志还写着「补齐描述与配色」**，实际只补了描述 | 两个管线都改成 日期闸 → **取色** → **订正** → 校准 → 落盘；`correct_from_candidates` 的 docstring 里写明这条前置条件 |
| 3 | 「待确认」标签产出侧写 `待确认`、清除侧只认 `待确认版本` | 原神的类型标签**永远摘不掉**，成了日历上的永久徽章 | 标签定义收进 `common/keys.py`；产出侧与清除侧都引用它 |
| 4 | 星铁接入同一套总纲优先 | —— | 同一套 `pending` 机制，但**只收当前版本**的总纲（旧版本会把两条认成一条、插重复） |

**实测**：绝区零 251 → **252 项**（+1 白名单守卫，当时口径），星铁 85 → 110 项，都离线全通过。

**经验（这条正是上面「总纲优先」那条教训的加强版）**：**离线的单元验证过不了「接线」这一关**。
`OUT_FIELDS` 少一个字段、两次循环换个先后，任何单测都绿，而功能整体是死的。
所以这两条都补了**自检守卫**（断言白名单内容，而不是断言行为），并且总纲优先这条路的
验收方式是**把整条 `run()` 的联网部分打桩跑三轮**：落盘 → 订正 → 稳态零重复。

### 2026-09-21 — 总纲优先落地 + 订正通道

**起因**：原定方案就是「总纲优先」，落地时因为「类型在去重主键里」退成了只取公告。
身份改造（身份不含类型）把那条阻碍拆掉后，这里做回来。

**收益不是省事，是提前**：总纲比活动自己的公告早得多——3.2 里「惊喜放映企划」
「先遣赏金-区域巡防」早 **12 天**，「数据悬赏-实战模拟」早 **35 天**；按公告落盘时这些活动
在日历上要等到公告发布（实测平均只早 2 天）。

**六条改动**：`parse.parse_version_activities`（按**后缀**「全新活动」定位段、下个编号段处
截断、解析 `content` 而非 `text`）；`_activities_from_notes` 产候选（默认类型 + `pending`）；
`keys.likely_recorded` 遇 `pending` 不跳过；`find_duplicate` 兜底集合放宽到
`ANNOUNCEMENT_ACTIVITY_TYPES`（修既有 bug：类型跨轮变化时主键失配、兜底也不进 →
`apply_events` **插重复**）；新增 `calibrate.correct_from_candidates`（按**标题**匹配，
**不动 id、不动日期**）；`apply_events` 白名单加 `pending`。

**离线验证**：两份总纲 fixture → 3.1 出 13 条、3.2 出 11 条；24 条里 21 条与数据文件里既有
条目逐条比中、**全部一致**；对现有数据跑一遍订正是空转（护栏拦住了）；`pending` 生命周期
走通（补不了 → 留标记 → 公告候选到 → 补齐清标记 → 再跑无变更）。

**实现时发现并修掉的坑**（原方案里没有）：**「假补」**。原方案写的是「候选与带 `pending`
的条目同身份时补字段并清标记」，没区分候选来自总纲还是来自公告——总纲候选**每轮都会再出现
一次**，于是每轮都会把标记清掉一次，而它补不了任何字段；下一轮预筛就按「已录入」跳过该活动
的公告正文，描述与配图**再也补不上**。离线模拟才暴露出来，`correct_from_candidates` 的
「跳过带标记的候选」就是为它加的。

**经验**：**缺口宁可留着，不能假补**。清标记是一个不可逆的状态变更，清之前必须确认「这个
来源真的补上了东西」——**幂等重放的候选不能当作补全来源**。

**副作用（已在 §1.2 兑现）**：数据文件新增 3 条；`id` 会带着落盘时的类型，之后类型被订正时
`id` 不变（`id` 永不改变是既有规则）→ id 与类型字面不一致，是预期行为。

### 2026-09-21 — 活动身份改造

**起因**：实测发现**活动名会跨版本重复**——「全新放送」在 3.0（米游社 76019201，
2026/06/17 ~ 07/28）与 3.2（09/09 ~ 10/20）各有一期，**同名同类型**。老的 `(类型, 标题)`
认不出这是两期，新一期会被**静默跳过**——星铁「位面分裂」当年就是这么丢的，后来靠一份
`DATED_KEYED_PREFIXES` 名单补救。

**改了什么**：活动类身份 → **(标题, 开始日期)**，不含类型。**不建名单**，因为活动名没有规律
（3.1 两个福利槽叫「云端礼赠」「『嗯呢』大派送！」，3.2 叫「全新放送」「『嗯呢』从天降」，
四个名字互不相同、也不复用），**名单要人来维护，而这个名字池每版本换一轮**。

同时：`find_duplicate` 加「同名 / 同类型 + 7 天」兜底（日期进了身份，被订正后主键会失配）；
新增 `keys.likely_recorded`（预筛拿不到候选日期，只能按标题认）；删掉被改动变成无用的
`alt_types`；`common/bilibili._resolve_year` 在月日非法时返回 `None`（原来会拼出
`2025-13-45` 这种非法串，**真漏进 YAML 会让前端 Zod 拒收整份文件**）。

**实测**：三条管线各自最新的产物逐条比对，**回归 0 条**（旧认得的，新也认得）；
预筛没有变差（原神正文抓取 2 → **1**，星铁 2 → 2，绝区零 0 → 0）；
端到端幂等（`python zenless/pipeline.py` 实跑，md5 前后一致）；离线自检绝区零 **201/201**。

**经验**：**判据要派生，不要建名单**——但派生的判据要经得起「同名跨版本」这种反例。
这里的做法是让身份带上**天然唯一**的那一维（开始日期），而不是去枚举哪几个名字会重复。

### 2026-09-21 — 方案落地 + 数据订正

**起因**：原神与星铁两条管线已跑通，绝区零做第三条。

**关键判断：绝区零是三条线里最容易的一条**，因为它的**停服更新公告是一份完整的版本总纲**
——版本更新日、版本结束日、该版本全部活动的起止、高难期数，全在一篇里。原先的草稿以为
「版本终点要按 42 天推、高难日期要纯猜」，**实测推翻了**（公告明写版本结束时间；
高难日期可由「更新后第一个周五 + 每周交替」推出，16 个手工日期里 15 个吻合）。

**落地时相对方案的三处偏离**：① 活动改取各自公告（总纲供不出类型）——**后被推翻**，
见上面「总纲优先」那条；② 活动排除**从名单改成 `活动说明` 后缀判据**（名单会过期，
写新公告的人不会通知我们）；③ `common/calibrate.py` **不动**（给它加类型是**无来源的死配置**：
绝区零没有独立于公告的第二个来源，那几类的日期本来就出自同一篇公告，自己校准自己没有意义）。

**实测**：真实跑通一轮，正文抓取 **成功 16 / 失败 0 / 风控 0**，跳过 11；产出 23 条，
其中 **17 条新增**（6 条命中已有）；校准给 4 条已有条目加了标记、把前瞻标题改成
`《绝区零》3.2 版本…`；**幂等**（连跑两轮，第二轮新增 0、条目数不变，正文抓取从 16 降到 5）。
一份真实抓取的公告列表 + B站动态 80 条存进 `fixtures/`，自检不联网。

**数据订正清单**（实测定出的既有数据错误，**已全部落盘**）见 §6.2。

**经验**：**草稿里的「只能猜」要先验证再信**。这次两条「只能猜」都被公告原文推翻了——
总纲明写版本终点、高难的期数足够推出网格。**动手前先读一遍真实公告的结构**，
比按经验假设格式省事得多。

## 5. 已定口径

1. **卡池标题**：沿用现有手工格式 `调频活动-A/B`（不改成官方频段名）
2. **高难自动化**：按 §1.4 的网格推
3. **网页活动**：用「正文有非图床外链」判据
4. **版本大活动**：用 `【活动常驻说明】` / `【丽都纪事】` 段标记判
5. **`危局强袭战0729` 不改**：已知例外，管线只推当前版本的期次，不会与它撞车
6. **活动收两个来源**（总纲 + 各自公告），按身份去重留公告那条
7. **福利类与三倍掉落类都收录**，类型用原神已有的自定义类型 `登录福利`；判据是「累计天数
   领奖」型（`累计登录` / `登录即可` / `邀请好友`），消费返利与试玩关卡不算
8. **常驻玩法开启不录入**（`EXCLUDE`），数据文件里已有的那条留着手工维护
9. **活动类的去重身份 = `(标题, 开始日期)`，不含类型**
10. **定时器不做**：用户自设 Windows 计划任务（2026-09-24）

### 6.1 公告结构与实测结论

| 公告标题形如 | 给出什么 |
|---|---|
| `X.Y版本「NAME」更新公告` | **总纲**：`【更新开始时间】`、`X.Y版本结束时间为 YYYY/MM/DD HH:MM，该版本共持续N天`、`X、全新活动`、`▶危局强袭战`/`▶式舆防卫战`（各 3 期，**只有敌人、没有日期**） |
| `X.Y版本「NAME」预下载开启&更新通知` | 只给 `【预下载时间】`；版本终点只说「截止至X.Y版本结束前」**不给日期**（所以不解析） |
| `X.Y版本限时频段（上期/下期）` | `本期代理人与音擎调频活动时间为：A ~ B` + 各频段的 S 级代理人与音擎 |
| `X.Y版本「丽都城募」说明` | `【活动时间】`（大月卡） |
| `「X」活动说明` | `【活动时间】`、`【活动奖励】`、`【参与条件】`、`【活动说明】` |
| B站官方动态（uid 1636034895） | 前瞻预告里的 `将于8月28日 19:30正式开启` |

> 段号**每版不同**（3.1 是 `七、全新活动`，3.2 是 `六、全新活动`），任何按段号定位的写法
> 都会过期。总纲里的活动名与单独公告的标题写法也不同（总纲 `• 「嗯呢」大派送！` vs 公告
> `「『嗯呢』大派送！」活动说明`）——**外层再包一层「」时，内层的「」要改写成『』**，
> 数据文件用的是后一种。管线不依赖这个转换：标题一律取自公告 subject 的最外层「」，
> 嵌套照抄。

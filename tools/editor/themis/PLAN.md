## 0. 交接速览（下次开工先读这一节）

- **未定的活动信息在米游社「资讯栏」（`type=3`），不在公告栏。** 公告栏只有运维帖，
  但**版本停服更新公告在公告栏**——两个栏目都要抓，别只抓一个。
  公告栏只取**版本号 + 开服日**（标题里都现成），`▌` 内容清单不解析。
- **预筛三道闸，先帖子 id、再标题、最后才取正文**：⓪ 帖子 id 已录入就跳过（不取正文，
  裁定 33）① 标题负向名单（丢 19/50，**不取正文**）② 正文解不出完整时段（再丢 11/31），
  ③ 礼包/商城复刻再丢 1 篇
  → **19 条候选 → 去重后 17 条 ＋ 版本更新 1 条 = 18 条 ≈ 3.6 条/周**。
  判据是「能否解出完整时段」而不是关键词名单，
  所以用户点名的四类（活动PV / 新卡展示 / 玩法预告 / 累充预告）全在内。
  ⚠️ ⓪ 按**帖子 id** 认（另三端按标题认）：未定的候选标题此刻还不是条目名；而且数据文件
  侧的标题从此不会被管线重算 ⇒ **改标题要手工同步改数据**（RULES §4.3）。
- **条目粒度 = 一篇帖子一条**；日期只认**本篇自己的时段**，不从兄弟帖回填。
  同主题的 3 篇预告 → 3 条；完全重复的（复刻 vs 本体）跳过。
- **标题取「活动名」，不取整条 `主题丨子标题`**：`丨` 前缀是**栏目名**
  （`往期复刻` ×3、`轮替女神之影` ×2、`商城上新` ×2 都会撞），
  取法见 RULES §4.2。已验证只取活动名**不会**造成重复条目。
- **未定不接 `common.calibrate`**（没有校准机制），管线**只增不改**；
  卡池身份因此**带开始日期** `(类型, 标题, 开始日期)`（返场标题逐字相同，
  不带日期会被静默跳过）。⇒ 日期只能手改 YAML，所以 §4.2 的日期兜底是必需的 ——
  而正因为日期不会被自动改写，未定走**精确口径**：同名同起日，或同源帖
  （`keys.EXACT_FALLBACK_GAMES`），**不借**三端那个 ±7 天窗口（借来只会静默吞活动）。
- **手工 19 条已与管线取法对齐**（改 5 条标题）。`「岁悦同欢·莫弈篇」生日拼图` 那四个字
  现在由**管线自己派生**（子标题里含 `生日拼图` 就接在标题后）—— 同一期活动的两篇帖子
  在日历上因此分得开，判定上也各靠自己的主键落位（RULES §4.2，裁定 30/31）。
- **复刻 / 返场帖的标题统一带 `限时复刻` 后缀**（裁定 32），接在活动名后面、引号外面：
  `「濯影拾辉」活动限时复刻` → `「濯影拾辉」限时复刻`。日历上一眼看出这是复刻；
  首开与复刻两期的标题也因此不同。⚠️ 分不了**轮替池的各期**（每期都是返场、都带后缀）
  —— 分期仍靠开始日期（裁定 18）。
- **颜色**：只有版本更新是固定 `#ffffff`，其余（含版本大活动、大月卡）走封面取色。
- **标签**自动打（男主名 + 稀有度 + 联动），标题优先、正文兜底；
  **活动描述一律留空**（RULES §4.7 / §4.8）。
- **版本大活动的判据 = 正文里的官方复合标签**（`大型〈季节〉活动` /
  `〈◯◯〉主题活动` / `〈◯◯〉联动活动`），排除 `限时` / `生日` / `周边` / `累充`。
  332 天全库**只命中 4 个活动、零假阳性**，且这 4 个刚好都是 17 天。
  标签**只在正文里**，标题（`subject`）没有；同一活动多篇帖子会**类型打架**，
  所以去重时**类型取并集、版本大活动优先**。详见 RULES §2.2 / §2.4。
- **版本大活动落不了是预期内的**：`NXX-非常假日` 8 篇里没有一篇带结束日，
  等下一篇带完整时段的公告即可，**不落 `pending` 半条数据**。
- **窗口很窄**：`getNewsList` **不能翻页**（`last_id` 返 0 条，`offset`/`page` 被忽略），
  `page_size` 上限 50（传 100 静默回落成 20）。资讯栏 50 条只有 **5 周**，
  比一个版本周期（约 42 天）还短。
- 日期口径：正文用 `▶活动时间：`（**没有 `〓〓` 段名**），结束时刻 `04:00` 要**减一天**，
  `11:00` / `23:59` 直接抄。⚠️ 这一步手工最容易漏：核对手工 19 条时，
  窗口内 12 条可核对的**有 6 条错**，3 条正是漏减一天（已订正，见 §4）。
- **B站 不接入**（UID `436175352` 已实测）：它与米游社**逐字同源**，零额外信息，
  且**没有 `subject` 字段**（`topic` 恒为 `None`），主题只能从正文 regex 抠。
  唯一优势是「单源 + 窗口深」（90 条 = 57 天），只对**首次回填**这一次性动作有用。

### 2026-09-25 — 复刻标题加 `限时复刻` 后缀 + 补「已录入就跳过」的预筛

**起因**：用户提了两件事 —— ① 复刻活动要在活动名后面加 `限时复刻` 后缀（日历上一眼看出
这是复刻），范围当场定为**往期复刻 + 轮替返场**、后缀写在**引号外面**；② 未定也补上另三端
那个「录入就跳过」的预筛。两件事最后咬在一起（见实测 4）。

**改了什么**

- `themis/rules.py`：新增 `REPRINT_TOPIC_PREFIXES`（`往期复刻` / `轮替女神之影`）、
  `REPRINT_SUFFIX = "限时复刻"`、收套话的 `REPRINT_TAIL_RE`
- `themis/parse.py`：新增 `is_reprint(topic, sub)`；`title_of` 里复刻分支**提到卡池分支
  之前**（复刻卡池也要带后缀）
- `themis/pipeline.py`：`collect(..., existing=())` 新增 ⓪ 预筛（按 `post_id` 跳过、
  记 `FETCH_STATS["skip"]`、判定表记 `跳过 / 已录入`）；`run()` 读数据文件传进去、
  日志加 `预筛跳过 N`、判定表新标记 `·`
- `selftest.py`：新增 `test_is_reprint` / `test_pre_screen`，改 `TITLES` / `EXPECTED` /
  `test_matches_existing` 的期望表 —— **106 → 124 项全过**
- `data/events/tears-of-themis.yaml`：**手工**改 2 条复刻标题、修 1 条指错的 `source_url`
  （`id` 不动，见实测 4 / 7）
- 文档：RULES 的漏斗/决策树/§4.2/§4.3/§5 差异表，PLAN 本节与 §5 裁定 32/33

**实测**

1. **7 篇复刻 / 返场帖逐条核对**（fixtures 全量，`test_titles` 锁住）：

   ```text
   往期复刻丨「濯影拾辉」活动限时复刻              → 「濯影拾辉」限时复刻
   往期复刻丨「心有所欲」活动限时复刻              → 「心有所欲」限时复刻
   往期复刻丨「NXX-冰原上的审判」活动女神之影限时复刻 → 「NXX-冰原上的审判」限时复刻
   轮替女神之影更新丨夏彦SSR【夏花永隽】限时返场    → 夏彦SSR【夏花永隽】限时复刻
   轮替女神之影丨莫弈SSR【莫负良辰】限时返场        → 莫弈SSR【莫负良辰】限时复刻
   往期复刻丨莫弈生日系列限时复刻                  → 莫弈生日系列限时复刻（收不出活动名）
   往期复刻丨「NXX-冰原上的审判」活动系列限时复刻   → 丢弃（礼包复刻，照旧）
   ```
2. **后缀的作用范围比预想的小**：原以为「加了后缀，返场就不用靠日期区分了」，实现时发现
   **轮替池每一期都是返场、每期都会带上这个后缀** ⇒ 标题仍逐字相同，**分期还是只认开始
   日期**（裁定 18）。后缀实际解决的是「首开 vs 复刻」与「日历可读性」，不是分期
3. **⓪ 预筛按帖子 id 认，不按标题认**：另三端那套 `likely_recorded` 在这里两头不成立
   —— 候选侧手里只有 `主题丨子标题`，条目侧存的是 `title_of` 推出来的活动名；放宽成
   「主题在条目里出现过」会踩 `岁悦同欢·莫弈篇`（9/17 拼图 / 9/20 本体，同名不同期），
   误判一次就是**静默少一条**。帖 id 是精确的：一篇帖子至多产出一条候选（裁定 9 的落盘粒度）
4. **两件事咬在一起**：预筛按 id 跳过之后，**数据文件侧的标题不再被管线重算** —— 所以本轮
   加后缀时，那 2 条已有复刻条目是**手工同步改**的（`id` 也刻意没改：它是前端「已完成」
   追踪键）。反过来，删条目就能让下轮重新产出
5. **预筛在窗口内命中 2 篇**（正文请求 31 → 29、候选 18 → 17，`test_pre_screen` 锁住）：
   手工那 19 条里只有 4 条带帖子 id。管线自己落的条目都带 `source_url`，命中率随轮次涨
   —— 收益在看趋势，不在这一轮
6. **预筛省的也可能是一条候选，但落盘不变**：`夏彦SSR【换日线】` 唯一的来源帖子
   （77910710）已录入 ⇒ 它不再产出；而 `爱的未定式·夏彦篇` 有兄弟帖（77933880）照旧产出
   同一条。两条都**已录入**，`apply_events` 本来也会跳过 ⇒ 少的是中间候选，不是日历上的条目
7. **同一帖 id 不该被两条条目共用**（顺手修的一处旧数据）：`夏彦SSR【换日线】` 的
   `source_url` 原本指着爱的未定式那篇（77934380），与那条**共用**。预筛按 id 认，
   指错就会让**被误指的那篇帖子**长期不产出候选 —— 已改成卡池帖 77910710

**经验**

- **后缀能不能当判据，取决于它会不会在别的期上重复出现。** 同一个后缀在轮替池上每期都出现，
  它就只剩「可读性」这一半作用 —— 判据部分还得靠日期。裁定下来时说的两件事
  （「一眼看出是复刻」+「两期标题不同」），落地后只有前者对整个范围成立。
- **预筛怎么认，是从落盘粒度反推出来的，不是又一份名单。** 「一篇帖子一条」这条结构决定了
  帖子 id 与条目一对一 ⇒ id 可以当预筛判据；三端的标题法在未定失效，同样是结构原因。
- **一对一的判据一旦反过来用，就得先确认「一对一」本身成立。** 预筛是「条目 → 帖子」的
  反向查询，只有在条目侧的帖子 id **指对了**的时候才精确；数据里已经有一处指错（实测 7），
  它不会报错，只会安静地少一条候选。

### 2026-09-25 — 收紧未定的日期兜底 + 后缀改由管线派生

**起因**：上一轮把「±7 天同名兜底会在空文件上吞掉兄弟条目」记成了**代价不可避免**，
判据停在「靠标题不同回避」。用户追问「以后类似情况也会少活动，有什么好办法吗」——
于是回头查这个窗口在未定到底为什么存在。

**改了什么**

- `common/keys.py`：新增 `EXACT_FALLBACK_GAMES = {"tears-of-themis"}`，未定的日期兜底
  从「同名 + ±7 天」换成「**同名同起日**」或「**同源帖**」（`post_id` vs `source_url`）；
  三端与不传 game 的调用点口径不变（口径挂在「这条线的日期会不会被 `calibrate` 自动
  改写 / 一篇公告会不会落多条条目」这两条机制上，不是又一份游戏名单）
- `themis/rules.py` + `parse.py`：主题兜底取标题时，子标题命中 `TITLE_SUFFIX_WORDS`
  （目前逐例一条：`生日拼图`）就把那四个字接到标题后（裁定 30）
- `selftest.py`：`test_identity` 补口径断言（未定不认「日期挨着」、三端仍认、同源帖认回、
  同名不同期各算各的）、`test_titles` 补后缀两例、`test_collect` 期望表与
  `test_matches_existing` 的命中方式改成主键 —— **106 项全过**

**实测**

1. **±7 天窗口在未定是借来的**：它存在的理由是「日期会被 `calibrate` 自动改写、改写
   幅度不限」，那是三端的性质。未定的日期只会被**人**手改，而手改的是**那篇帖子产出的
   条目** ⇒ 帖子 id 就是精确判据，窗口纯属多余
2. **两种出错的代价不对等**：窗口的假阳性 = **静默吞掉一条活动**（不可见）；
   精确口径的假阴性 = 多一条**可见的**重复（删一次）。所以取窄
3. **实测代价为 0**：数据文件里 6 次人工订正**全是 end_date**、起点一次没改过
   —— 精确口径在当前数据上不产生任何重复。踩到的正是 `岁悦同欢·莫弈篇` 那两条，
   新旧口径的逐候选对照：

   ```text
   旧口径（±7 天）：候选 9/17 → 主键 (「岁悦同欢…」, 09-17) 失配
                            → 兜底：同名的 09-20 在 7 天内 ⇒ 判为重复 ⇒ 跳过
                  候选 9/20 → 主键直接命中                       ⇒ 跳过
   新口径（精确）：  候选 9/17 → 主键 (…生日拼图, 09-17) **直接命中** ⇒ 跳过
                  候选 9/20 → 主键命中                           ⇒ 跳过
   ```

   旧口径下 9/17 那条**落不了盘**（空文件时文件里只有管线落的 9/20，9/17 随后被判成
   重复 ⇒ 生日拼图这条活动直接消失，日志只显示「跳过 1 条」）；新口径下两条各靠自己的
   主键落位，任何轮次、任何先后顺序都成立
4. **后缀能由帖子自己派生**：`岁悦同欢·莫弈篇丨生日拼图限时活动预告` 的子标题就是
   `<短语><公告套话>`，剥掉套话的短语正是手工写的那四个字 ⇒ 派生结果与手工那条
   **逐字相同**，两边不用互相迁就，也不必再靠人记着
5. **名单宁窄勿宽**：同一活动的另一篇 `莫弈生日活动预告` 若也剥（把 `预告` 当套话），
   会得到 `莫弈生日活动` 这个多余后缀，还与同组那篇打架 —— 逐例补充比通用解析稳
6. **改动本身零代价**：收窄前后各离线跑一遍「候选 × 真实数据文件」的累积去重，
   **8 新增 / 10 跳过逐条相同**；空文件场景（只留 9/20 那条时喂 9/17 候选）从
   「判为重复」变成「不重复」。星铁 144 / 绝区零 255 自检全过。

**经验**

- **借来的判据要问清它的适用条件。** 复用一段已经跑通的逻辑之前，先问「它为什么能成立」
  —— 窗口靠的是「日期会被自动改写」，借到「日期只被人手改」的端点上就只剩假阳性。
- **同一条信息可能兼着两种用途，改之前先分清。** 后缀原先兼着「判定上分得开」；
  判定收窄后它只剩「日历上看得清」，实现方式（手工写 → 管线派生）这才跟着变。

### 2026-09-25 — 写管线 + 自检 + dry-run

**起因**：规则探明之后落成代码 —— `themis/` 五个模块，接进 `maintain.py` 当第四端。

**改了什么**

- 写 `themis/`：`rules.py` / `parse.py` / `pipeline.py` / `selftest.py` / `fixtures/`，
  接进 `maintain.py`；`common/` 侧只动了三处（`keys` 的卡池身份与兜底、
  `yaml_io` 的两个映射、`extractor.fetch_post_list` 的 `news_type` 参数与 `apply_events` 传 game）
- 自检 101 项（含拿 fixtures 对着数据文件交叉比对）
- dry-run 实盘：31 篇正文里遇到 **1 篇风控 1034**，判定表逐篇核对
- 数据文件改 3 条标题（§5）

**实测**

1. **卡池信号要取整条标题或正文**：`往期复刻丨莫弈生日系列限时复刻` 的子标题里
   没有 `女神之影`，信号只在正文（正文通篇女神之影、两段不同时段的卡池）。
   放宽后实测标题含 `女神之影` 的 4 篇**全是卡池、零假阳性**
2. **`上架` 要进丢弃集**：`往期复刻丨往期绮思限定甜心服饰常驻上架短笺兑换所`
   （9/30~10/17）有**完整时段**，第二道闸拦不住；主题是往期复刻所以躲过了 `商城上新`
3. **标签「标题优先、正文兜底」**：按名字/稀有度分别兜底会多打标签
   —— `「爱的未定式·夏彦篇」` 正文写着 SSR 而手工 tags 只有 `夏彦`；
   而两条轮替返场帖的正文列着整个轮替池（四人 + SR），只看正文会打成四人全中。
   整条标题有命中就整条不看正文，19 条手工数据里标题能对上的 10 条**全部逐字吻合**
4. **±7 天同名兜底会在新文件上吞掉兄弟条目**：`岁悦同欢·莫弈篇` 的生日拼图（9/17）
   与生日活动（9/20）同属一期、只差 3 天，两条若同名就会丢一条。
   今天没事是因为手工条目**标题本来就不同**（`…生日拼图`），对齐时故意留着后缀
   > 当天晚些已改掉：窗口本身在未定没有存在理由，判定换成精确口径、后缀改由管线派生
   > —— 见本节最后一条开发记录
5. **手工那 3 条带后缀的标题会让首轮插重复**：`「星航寻梦」-左然MR【幻航】` 这类
   与管线取的「活动名」不同 → 主键失配、兜底也认不出（兜底按标题逐字比）。
   对齐后 18 条候选从「11 新增」变成「**8 新增 / 10 跳过**」
6. **「标题只取活动名」不会造成重复条目**：8/21–9/25 的 26 条候选**内部零同名**；
   与手工 19 条的 4 处疑似碰撞（`「濯影拾辉」活动限时复刻`、`「NXX-冰原上的审判」
   活动女神之影限时复刻`、`夏彦SSR【换日线】`、`「秋颂绮思」`）逐条核过，
   **全都是同一个活动** ⇒ 这条取法可以落地
7. **「思绪帖」那道判据是多余的**：草案打算单独挡 `…活动限定夏彦SSR【惟愿得偿】`
   这类新卡展示帖，实测它们正文里**都没有完整时段**，第二道闸已经全部拦下；
   而带完整时段的思绪帖（`轮替女神之影丨莫弈SSR【莫负良辰】限时返场`）本来就该是
   卡池，单独挡反而会漏 ⇒ 判据只留「有完整时段才进候选」一条
8. **卡池不需要「取色排在订正之后」**：草案照搬了三端那条硬约束（那边的卡池日期
   会被订正改写），而未定的卡池日期就是**卡池帖自己的** `▶活动时间` ⇒ 这条顺序约束
   在未定没有对应物。**借来的顺序约束和借来的判据一样，得先找它的前提还在不在。**
9. **漏斗数字与草案稿不同（14 / 16 / 17 → 19 / 17 / 18），差别不在判据松紧而在口径**：
   ① 草案把 `教师节快乐丨…` 算成了误杀 —— 它的时段行是裸的 `▶2026年9月10日00:00-…`
   （无 `活动时间：` 标签），解析器同时认**带标签**与**裸 `▶日期`**两种写法，
   所以它现在是候选；② `上架` 那一篇当时还没发，现在进了丢弃集。
   表中每个数字都能在 `test_collect` 里复现（§6.2.1）

**经验**

- **判据的边界要在「反例所在的样本」里试。** 卡池信号原本只查子标题，`轮替返场` 的
  信号在主题里（实测 4/4 命中）—— 只看子标题会漏掉整类轮替卡池；
  而 `女神之影` 一旦放宽到「正文也查」，就必须回头确认另外 3 篇复刻帖正文 0 命中，
  否则会把礼包复刻也放进来。**放宽判据的成本是重新数一遍反例，不是放宽本身。**
- **同一活动拆多篇的代价是双向的**，这里暴露成「同名不同活动」：
  管线按标题认身份，`岁悦同欢` 一期两条就差 3 天 —— 手工后缀看着像冗余，
  其实是身份判据里**唯一能把它们分开的东西**。删之前先问「这条信息还有谁在用」。
  （后缀的**角色**后来变了：判定不再靠它分开，它只剩「日历上看得清」这一种用途。）
- **风控的表现是「结果变少」，不是「报错」。** 那 1 篇 1034 丢掉的帖子本来就解不出时段，
  结果完全相同 —— **只有日志里的计数能区分「今天风控了」与「今天没有新活动」**，
  所以 `FETCH_STATS` 把 `risk` 单列出来。

### 2026-09-25 — 验「分阶段」线索 → 复合标签判据（收尾）

**起因**：版本大活动的判据还悬着。手里最像的线索是「正文写『分阶段开启』」
（`何人生还` 4 幕、`NXX特别调查` 多阶段）—— 线索要验到底，不能停在「看着像」。

**改了什么**

- 上一条线索是「版本大活动正文写『分阶段开启』」。抓 **500 条 B站 动态
  （2025-10-28 ~ 2026-09-25 = 332 天）** 把这条验到底 —— 不是抓够一个版本，是
  抓够**四个版本大活动**
- 全量抽「活动标签」句式：把 `〔修饰语〕活动「活动名」` 在 500 条里跑了一整遍

**实测**

1. **「分阶段」不成立**：它有**两个互不相干的意思**。剧情分阶段解锁（何人生还 4 幕）
   与累计进度「达到指定阶段」（`邂逅波光`/`邂逅幻梦` 的甜蜜值阶梯，都是常规活动）。
   按「≥2 行 `M月D日…第X幕/阶段`」跑全库会命中常规活动 `绮乐环游记`；
   而 `旧梦今情`/`萌兽在校生`/`心语启扉` 的相关帖子（11/21/17 篇）**一条都不含「阶段」**
2. **复合标签判据成立**：332 天里 `大型〈季节〉活动` / `〈◯◯〉主题活动` /
   `〈◯◯〉联动活动` **只命中 4 个活动、零假阳性、一句一期**（四个活动的表见 §6.6），
   且 4/4 全是 **17 天**
3. **5.7 与 6.0 没有版本大活动** —— 不是漏抓，那两版的 `▌` 第一条只是
   每版一期的篇活动系列（官方自称「限时活动」，各 6–7 天）
4. **同一活动多篇帖子类型会打架**：`「何人生还」` 3 篇帖子时段完全相同
   （`7/15 11:00-8/2 04:00`），只有带标签的那几篇能判成版本大活动；
   去重若单纯「跳过」，类型取哪个取决于**处理顺序** ⇒ 必须带 tie-break

**经验**

- **判据要在「样本比你需要的更宽」时才敢下。** 「分阶段」线索在 5 周窗口里
  看着挺像（何人生还 + NXX特别调查 两条命中）；放到 332 天里立刻暴露
  「另一类常规活动也这么写」。**判据的反例往往不在你为它准备的样本里** ——
  这也是为什么原神侧的「时长」判据在 19 条里就自己崩了。
- **零假阳性比高命中率值钱。** 复合标签 332 天只命中 4 次，看着「覆盖率低」，
  但它的每一次命中都对、且**一句一期**正好是版本大活动的真实频率
  （6 版里 4 版有）——「命中少」不是缺点，「为什么少」说得清才是。
- **一个活动拆成多篇发，会连带把「类型」也拆散。** 前面只记了「日期散在别的帖里」，
  没料到**分类标签也散**：yaml 引的那篇 `76662839` 正文里连「阿加莎」都没有。
  「完全重复就跳过」这条老规则在**单源标题即身份**的三端够用，
  换到「同一活动多篇帖子」的未定就必须补 tie-break。

### 2026-09-25 — 核对手工数据日期 + 时长判据

**起因**：数据文件里那 19 条是手工录的，它们既是日历上仅有的存量，也是后面所有判据的
对照组 —— 得先确认它们本身没写错；顺带把「版本大活动时长更长」这个候选判据验一下。

**改了什么**

- 拿正文（有 `source_url` 的直接 `fetch_post`，其余用 8/21–9/25 语料里的时段）
  逐条核对手工 19 条的日期，**订正 6 条**
- 统计「版本大活动是不是时长最长」—— 否
- 顺带用同样的数据否掉了「三件套」判据

**实测**

1. **手工数据错误率 50%**：窗口内 12 条可核对的**有 6 条错**，3 条漏减一天
   （心语启扉 `8/27→8/26`、青葱寄愿 `9/6→9/5`、NXX特别调查 `9/16→9/15`），
   3 条数量级错误（彤心欲眠 `10/20→8/26`、濯影拾辉 `9/30→8/31`、
   秋颂绮思 `9/14→10/14`）
2. **时长判不出类型**：「何人生还」17 天，但常规活动里有 24、19 天的
   （「邂逅幻梦」24 天经正文核对**是真的**），大月卡「秋颂绮思」34 天
3. 三件套（徽章 + 名片 + 邀请函）也分不开 —— 命中它的是生日/篇章类常规活动

**经验**

- **订正过的数据会反过来推翻结论。** 时长判据第一次统计时给出的是
  「最长的是卡池 61 天 / 常规 34 天」，看着像能分出「版本大活动不在最长那档」；
  但里面**两条是录入错误**（彤心欲眠、濯影拾辉）。核完真值，结论变成了
  「常规活动里就有 24、19 天的」，**方向相反**。统计口径对不对，取决于数据本身，
  所以**下结论前先把样本逐条核对一遍**，尤其样本量只有十几条的时候。
- **「不在名单里」和「名单里没有」是两回事。** 判断公告能否给出「版本大活动」
  这个标签时，我先看到 5.6/5.8 的第一条是「…主题活动」就以为规律成立；
  实际 5.9 的第一条是**卡池**，而且 `「何人生还」` **压根不在** 5.9 的 `▌` 里。
  反例要找**唯一性**，不是找一个像样的正例。

### 2026-09-25 — 补测：B站 动态对比 + 翻页能力

② 资讯栏 50 条只有 5 周，能不能翻页决定了**首次回填**这件事有没有可能。

**改了什么**

- 拿到未定 B站官方号 UID `436175352`，抓 40 条做结构对比，再抓 90 条（57 天）
  覆盖一个完整版本周期
- 测 `getNewsList` 的翻页参数（`last_id` / `offset` / `page`）

**实测**

1. **B站 与米游社逐字同源。** 36/40 条能对上；对上的文本差异只有 B站 的前缀
   `#未定事件簿#【子标题】` 和尾部一行 `※点击查看…↓↓↓`
2. **B站 没有 `subject` 字段**（`module_dynamic.topic` 恒为 `None`）→
   分组信息只能从正文 regex 抠，比米游社差一档
3. B站 单 feed 同时含活动与**版本停服更新公告**（`DYNAMIC_TYPE_ARTICLE`，
   90 条里 1 条正是 6.0 停服公告）
4. B站 feed 非严格时序（40 条里 1 处逆序，置顶/聚合导致）
5. **米游社 `getNewsList` 不能翻页**：`last_id` 返回 0 条，`offset` / `page`

6. 一条**假阳性**：B站 的 `▶活动时间：2026年9月30日更新后-10月18日04:00`
   看着像米游社没有，实为抓取时机差（米游社那条 11:30 才发）

**经验**

- **做源对比必须两侧同时抓。** 我差点把「时机差」当成「B站 独有信息」——
  这是这类对比最容易出的错，而且错了会直接导致「多接一个源」这种没人需要的结论。
- **「无额外信息」要证明到逐字。** 只比对「有没有某条日期」不够，得把同一篇的正文
  归一化后 diff，才能说清「差异只是那两处装饰」。做了这一步，结论才是硬的。

### 2026-09-25 — 前期分析：抓 95 篇看规律

**起因**：未定这端此前只有一条猜测（「活动可能在资讯栏」），连公告长什么样都没抓过。
要接自动化，先得把两个栏目抓一遍，把标题与日期的实际形态摊开看。

**改了什么**

- 抓 `gids=4` 两个栏目各 50 条列表，再抓 95 篇正文（资讯栏 50 + 公告栏的版本/日常更新
  公告），**全部成功、零风控**
- 按主题前缀、日期标记、图片数逐篇统计，产出 [RULES.md](RULES.md) 与本文

**实测**

1. 活动在资讯栏、版本公告在公告栏 —— **必须两个栏目都抓**（此前只把 `type` 改成了 3）
2. **一半的帖子正文没有日期**，日期在同主题的另一篇帖里；一个活动拆成最多 8 篇
3. 正文没有 `〓〓` 段名，标记是 `▶活动时间：` / `※活动时间：`
4. 结束时刻是 `04:00`（原神写 `03:59`，同一个游戏日边界）→ **减一天**；
   `11:00` / `23:59` 直接抄
5. `page_size` 上限 50，超过会**静默回落成 20**
6. 版本周期不稳：37 / 42 / **70** / 42 天 → 不能像原神那样写死 42 天外推
7. 资讯栏 50 条只有 5 周，`pending` 摘不掉的风险比绝区零更高

**经验**

- **「两个栏目」这种事只能靠实际抓一遍发现。** 我前面刚把 `type` 改成 3 就以为修好了，
  其实只修了一半——停服更新公告还在 `type=1`。分类修完不等于数据源修完。
- **「标题像不像活动」在未定完全不可靠**：`丨` 前缀是所有帖子的命名法，
  `插画分享` 和 `活动玩法` 长得一模一样。**它什么都不能用来判** —— 分类不能靠它，
  当初以为的「分组取日期」也推翻了。
- **日期不在正文里这件事，统计之前看不出来**。95 篇一跑，「有 / 没有」接近 1:1
  这个比例才是决定方案的东西。不过**当时推出的是错的结论**：我由此认定管线必须
  「按主题归并、组内取有日期的帖」。实际上裁定 6（一篇一条）+ 裁定 9（落不了就等）
  之后，**归并这一步根本不需要** —— 无时段的帖直接丢就行，剩下的 16~17 条
  每篇自带日期。**「看似需要归并」是统计比例给的错觉，不是真需求。**

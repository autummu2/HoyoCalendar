# 活动信息提取规则（原神）

自动化维护活动信息时，从公告/动态中提取字段的规则依据。当前覆盖**原神**；星铁、绝区零的规则后续按各自公告格式补充。

## 数据来源

| 来源 | 用途 |
|---|---|
| 米游社公告栏（`fetch_post_list` / `fetch_post`） | 主来源：常规活动、版本大活动、祈愿、网页活动（标题 + 描述）；另含**版本更新维护预告**（更新前 ~2 天发，给出日期 + 版本号 + 版本名） |
| B站原神官方账号动态 | 补充来源：卡池日期（米游社公告是图片、读不到）、活动日期（版本大活动米游社是图片、读不到）、版本大活动判定（多阶段信号）、前瞻直播时间、版本名 |

## 模块分工

| 文件 | 职责 |
|---|---|
| `extractor.py` | 米游社公告抓取 + 分类（按标题）+ 正文解析 |
| `bilibili.py` | B站动态抓取 + 解析 + 与米游社结果合并（B站命中时带 `source` 字段标明权威来源） |
| `inference.py` | 周期性事件推理（纯函数，锚点由调用方从数据文件推导后传入） |
| `keys.py` | 条目主键（身份判定），新增与校准共用 |
| `calibrate.py` | 用权威来源校准已有条目（纯函数），打 `calibrated` 标记 |
| `apply_events.py` | 新增落盘（只新增，不改已有条目） |
| `run_pipeline.py` | 驱动整条管线，产出 `extracted_full.json` |
| `maintain.py` / `maintain.bat` | 外部一键入口：`run_pipeline` → `apply_events`，stdout 追加写入 `logs/YYYY-MM-DD.log` |

> 前瞻特别节目不在米游社公告栏里，需去**资讯栏**或 **B站动态**获取。B站接口/账号 uid 待实现时确认。

> ⚠️ **米游社正文接口有风控**（`retcode 1034`，`message` 为空）。公告列表（`getNewsList`，static 域名）不受影响，所以典型特征是「列表拉得到、正文全失败」。连续多次运行会触发，且反复重跑会加重。此时正文抓不到的条目拿不到日期 → 被日期闸丢弃 → 本轮报「0 新增」，看起来像「今天没有新活动」，属**假阴性**；数据本身安全（新增只插不改、校准找不到来源就不标记、推理走数据文件锚点不碰网络）。详见 §九。

> ⚠️ **B站动态的文案格式会随版本变动**（例如前瞻公告 7.x 起才带版本号、6.x 是嵌套书名号；卡池有「预告」与「总览」两种、结构不同）。`bilibili.py` 里的解析函数依赖这些格式，抓取结果异常时优先怀疑格式变动，按实测重新校准，别硬套旧规则。

## 一、时间与日边界

- 游戏内一天 = 当日 `04:00` → 次日 `03:59`。
- 公告时间格式固定：`YYYY/MM/DD HH:00 ~ YYYY/MM/DD 03:59`（开始整点、结束 03:59）。
- **start_date** = 开始时间所在日，直接抄（开始是 10:00/04:00 这类白天整点，无需调整）。
- **end_date** = 结束时间 `X日 03:59` 的 `X日 − 1`（最后一个完整游戏日）。
  - 例：`~ 2026/09/17 03:59` → `end_date = 2026-09-16`。
- **卡池例外**：祈愿结束于 `17:59` / `14:59`（非 03:59），结束日直接抄、**不减一天**。
  - 例：`~ 2026/09/22 14:59` → `end_date = 2026-09-22`。
- 版本更新维护在 `06:00` 进行（非 04:00/03:59），记**单日**（start = end = 更新日）。

## 二、标题规则

| 类型 | 标题取值 | 示例 |
|---|---|---|
| 卡池 | **米游社公告标题**整段，去尾部 `！` | `「冰绡鹄影」祈愿：「翾风回雪·奥黛塔(冰)」概率UP` |
| 常规活动 | 取第一个 `「...」` 括号内活动名，去掉 `活动：玩法` 后缀 | `「悠悠律动舞力聚会」` |
| 版本大活动 | 括号内活动名 | `「险境征者竞锋大赛」` |
| 版本更新 | `《原神》X.X 版本「版本名」停服更新` | `《原神》7.1 版本「往冥府的安魂歌」停服更新` |
| 前瞻直播 | `《原神》X.X 版本「版本名」前瞻特别节目` | — |
| 周期性高难 | 合成标题 | `深境螺旋MMDD` / `幻想真境剧诗MMDD` |
| 网页活动 | 公告标题整段（括号统一用全角 `「」`） | `「至冬将至」网页活动` |

> 例外：`「七圣召唤」热斗模式：自行巧局`、`「七圣召唤」铸境研炼：…` 这类，括号内是**系统/玩法名**而非活动名，**保留完整标题**，不能只取括号。

## 三、各类型日期来源

| 类型 | 日期来源 |
|---|---|
| 常规活动 / 版本大活动 | 米游社正文 `〓活动时间〓`（兜底）→ **B站动态 `〓活动时间〓`（优先）**：B站给全阶段起止，版本大活动米游社是图片、只能靠 B站 |
| 版本更新 | **推理**（先占位）→ **米游社维护预告**（更新前 2 天发，正文含日期 + 版本号 + 版本名，最权威）→ B站前瞻公告（只有版本名，更早） |
| 前瞻直播 | **推理** → **B站前瞻公告**（含确认日期与版本名） |
| 卡池 | **版本节奏推理**（先推断，`infer_banner_dates`）→ **B站总览**（后校验覆盖，米游社卡池正文是图片、读不到日期） |
| 深境螺旋 / 幻想真境剧诗 | **推理**（无公告） |

推理出的条目只是**占位/新增**；已有条目的后续修正一律走第四节的校准流程。

## 四、周期性推理规则

- **版本更新**：固定在**周三**，版本周期 **42 天**。（7.0 = 08/12，7.1 = 09/23，均周三、差 42 天）
  - **锚点从数据文件推导**（`inference.extract_version_anchor`）：取最新一条「版本更新」的日期 + 标题里的版本号，**不硬编码**。版本延期或版本号跳号只需人工改数据文件里那一条，后续推理自动跟着走。
  - **「版本期间持续开放」的 end** = 下个版本更新日 − 1 天。活动属于最新已知版本时数据里还没有下一个版本更新日，按 42 天周期补一期兜底（`resolve_version_period`），否则 end 缺失、条目会被日期闸丢弃。
- **版本号 / 版本名**：版本更新前约 2 周（前瞻直播）才公布。推理时版本更新事件先占位（日期已知，版本号按 +0.1 预测、版本名留空），前瞻后据公告校正版本号并回填版本名。每个大版本的小版本数不固定（1.x 有 7 个，2.x~5.x 有 9 个），故版本号也只作预测、不做进位假设。
- **前瞻直播**：约在版本更新前 10~12 天，通常周五/周六。（7.0 前瞻 07/31 周五，7.1 前瞻 09/12 周六）
- **卡池**：上下半各 3 周。上半 = `[版本更新日, 更新日+20]`，下半 = `[更新日+20, 更新日+41]`（更新日固定周三）。版本更新日从数据文件「版本更新」事件读出（`extract_version_dates`）；阶段按公告发布时间相对**最近的版本更新日**判定：发布日 < 最近更新日 → 上半，否则下半（上半公告更新前 2 天发、下半更新后 15 天发）。逐条就近匹配，跨版本混排也能判对。B站总览出来后用其日期覆盖（权威）。
- **深境螺旋**：每月 **16 号**刷新一次，一期 `16号 ~ 次月15号`。每月一期（旧版每月两期的规则已废弃）。
- **幻想真境剧诗**：每月 **1 号 ~ 月末**。

## 五、公告分类（按标题判断）

**只按标题判断，不看正文**（正文关键词命中容易误杀）。

活动识别（`extractor.find_activity_announcements`）按「负向排除 + 剩余皆活动」：

1. 标题命中**负向/卡池/高难关键词** → 跳过。
2. 其余带 `「...」` 括号的 → 活动（常规活动 / 版本大活动，类型另由 B站动态判定）。

**负向关键词（跳过）**（`ACTIVITY_SKIP_KEYWORDS`）：

- 首充双倍、集中反馈、优化说明、版本更新、维护预告、更新说明、版本说明、更新修复、更新维护
- 赛季开启、装扮上新、冒险助力礼包、设备性能要求
- 云·原神、游戏问题
- **世界任务说明**（正文用 `〓任务开放时间〓`，不在记录范围内，直接跳过）
- 纪行（大月卡，如霜游纪行，另由 `find_battle_pass_announcements` 提取为大月卡）
- 卡池祈愿，按**精确特征**排除：标题含 `概率`（普通祈愿，`find_banner_announcements` 处理）或 `溯光祈愿` / `集录祈愿`（特殊祈愿，`find_special_banner_announcements` 处理）
  - ⚠️ **不可用宽泛的 `祈愿` 二字排除**：会误杀标题里恰好带「祈愿」的常规活动。实例：`「巡历雪境，凝铸锋锐」：自选邀请「奔行世间」常驻祈愿5星角色` 曾被整条丢掉。

**高难关键词（跳过）**（`CHALLENGE_KEYWORDS`，高难挑战有独立类型）：

- 危战、深境螺旋、深渊、幻想真境剧诗、混沌回忆、忘却之庭

> 关键词表为初始版本，随公告标题实际观察持续补充。

## 六、身份、去重与校准

### 6.1 主键 = 身份（`keys.event_key`）

「两个条目是不是同一个活动」只由主键决定，**与日期无关**。日期是**值**，会被校准修改；
主键是**身份**，一旦确定就不再变。混用两者会导致日期一改旧条目就认不出来 → 重复插入。

| 类型 | 主键 | 说明 |
|---|---|---|
| 卡池（普通/特殊） | **完整标题** | 标题格式随版本变（武器池 7.0 无 `「神铸赋形」` 前缀、7.1 有），所以不做括号解析 |
| 常规活动 / 版本大活动 | 完整标题 | |
| 大月卡 | 完整标题 | 纪行名每期不同（霜游纪行 / 溯月纪行） |
| 幽境危战 | **米游社公告 post_id** | 标题每期一字不变，只能靠公告 id 区分 |
| 版本更新 / 前瞻直播 | **(类型, 版本号)** | 标题与日期都会变（补版本名、前瞻改期） |
| 深境螺旋 / 幻想真境剧诗 | (标题, 开始日期) | 无公告，标题自带 MMDD，带年份防跨年撞 |

- 版本类事件另加**日期兜底**：主键失配时，同类型且开始日期相差 ≤7 天视为同一事件
  （`keys.find_duplicate`）。版本号是朴素 +0.1 预测、且标题一旦生成就不再改号，可能预测错。
- **`id` 与主键无关，且永不改变**：前端用 `id` 做 React key 与「已完成」追踪，改了会丢用户的完成标记。

### 6.2 新增（`apply_events.py`）

**只新增，不改动已有条目。** 主键已存在 → 跳过。因为主键与日期无关，日期被校准改动过的
条目仍能被认出，不会重复插入。`id` 由 `gi-{类型前2字}-{YYYY-MM}-{标题去符号取前8字}` 生成，
若撞已有 id 则加序号（id 必须唯一）。

### 6.3 校准 / 修正维护（`calibrate.py`）

用外部权威来源核对**已有**条目的日期：一致 → 打标记；不一致 → 改成权威值再打标记。

| 类型 | 校准依据 | 标记值 |
|---|---|---|
| 卡池 | B站总览公告 / 特殊祈愿动态的 `〓祈愿时间〓` | `B站总览` / `B站祈愿时间` |
| 版本大活动 | B站活动动态的 `〓活动时间〓` | `B站活动动态` |
| 前瞻直播 | B站前瞻公告（版本名 + 确认日期） | `B站前瞻公告` |
| 版本更新 | **米游社维护预告**（日期 + 版本号 + 版本名）；无预告时退回 B站前瞻补版本名 | `米游社维护预告` |

- **常规活动、大月卡、幽境危战、深境螺旋/幻想真境剧诗不校准**：前者没有可靠的 B站日期来源
  （B站活动动态只覆盖多阶段的版本大活动），后者无公告、本就走推理。
- **标记字段 `calibrated`**（值为上表来源名）：有标记 = 已确认，**不再重复处理**；
  本轮找不到依据就**不打标记**（下次再试），避免「假确认」。`EventSchema` 不是 `.strict()`，
  前端 Zod 会静默丢弃该字段，界面无感。
- **只处理 start_date 在最近 30 天内的未标记条目**：更久远的即便有错也已无意义，
  且来源动态早被 B站列表翻页刷掉，永远等不到依据（会一直白跑）。
- 只覆盖 `title / start_date / end_date` 三个值字段，其余（id/color/description/source_url…）一律不动。
- **匹配逻辑与提取阶段共用同一组函数**（`merge_activities` / `merge_banners` /
  `merge_special_banners` 等），避免两套实现漂移：这些函数在 B站命中时会带上 `source` 字段，
  `run_pipeline._build_sources` 据此汇总成权威值索引。
- 由于是「只新增 + 一次性校准」，**不需要状态文件，也不存在与人工干预的冲突**：
  人工改过的条目若被权威来源确认过就带标记、不再被动；版本延期只需人工改一次版本更新日期，
  后续推理自动跟着走（锚点从数据文件推导）。

### 6.4 校验

- **写入前校验**：`id / title / start_date / end_date` 非空，日期匹配 `YYYY-MM-DD`。
  前端对整文件做 Zod 校验，一条坏数据会让该游戏全部活动不显示。
- **日期闸（三层防护）**：① `parse_activity_body` 认不出的段 → ② `run_pipeline` 输出前丢弃
  无完整日期的条目并报告 → ③ `apply_events` 再兜一次。任何一层单独存在都不够，
  下次再来个新格式仍会漏。被丢弃的条目会在运行日志里以 `x` 列出。
- **dry-run**：先出「新增 X / 跳过 Z」预览，确认后再落盘。
- **幂等**：连跑两次，第二次必须 0 新增 0 校准、且 YAML 字节级不变。

## 七、常规活动 / 版本大活动提取

流程：米游社识别 → 抓正文 → B站动态判定类型 + 补日期（`merge_activities`）。

**类型判定（默认常规活动）**：

- 默认 `常规活动`。
- B站动态的 `〓活动时间〓` 段含 `阶段` / `结束时间`（多阶段，如竞锋大赛「第一阶段/第二阶段/…/结束时间」）→ `版本大活动`，打 `待确认` 标签。
- 判定为版本大活动只作「待确认」，最终类型需人工核对。

**日期（B站优先）**：

- B站动态 `〓活动时间〓` 两种格式，均取「首日期 = start、末日期 = end（03:59 减一天）」：
  - 常规活动（单段）：`2026/09/14 04:00 ~ 2026/09/21 03:59`
  - 版本大活动（多阶段）：`第一阶段：… / … / 结束时间：2026/09/14 03:59`
- 米游社正文兜底（`parse_activity_body`），三况：
  1. 完整 `X ~ Y 03:59` → start/end；⚠️ 遇「整体活动时间 X~Y / 任务完成时间 X'~Y'」时取第 2 个日期（整体结束），不能取最后一个（会误取任务截止日）
  2. `版本更新后 ~ Y` → 仅 end，start = **距发布日最近的版本更新日**（`inference.resolve_version_starts`）
  3. 无日期（图片，多为版本大活动）→ 靠 B站
- `版本期间持续开放`（如铸境研炼）→ start = 距发布日最近的版本更新日，end = 下版本更新日 − 1 天（`inference.resolve_version_period`）。
- ⚠️ 「版本更新后 / 版本期间」活动多在版本更新**前 1~2 天**发预告，判定所属版本要用「距发布日最近」，不能用 `≤ 发布日` 或 `≤ end_date`（会把预告归到上一版本）。
- `永久开放` → 不进日历。

**特判（已确认）**：

- `纪行`（如霜游纪行）= 大月卡，由 `find_battle_pass_announcements` 单独识别，日期取正文「版本更新后 ~ Y」（start 由 `resolve_version_starts` 补）。
- `溯光祈愿` / `集录祈愿` = 特殊祈愿（角色池大），归 `卡池`，标题**只写祈愿名、不写具体角色**（如「辉天的星告」祈愿：溯光祈愿开启）；日期同普通祈愿（`infer_banner_dates` 推断 + B站动态补充）。
  - **B站补充（已校准）**：特殊祈愿 B站动态不含「本期活动祈愿时间」（那是普通祈愿总览专用），而是 `〓祈愿时间〓` 段，两种格式：
    1. 上半：`「版本名」版本更新后 ~ Y 17:59` → 无显式 start，start = 版本更新日（`merge_special_banners` 取距动态发布日最近的版本更新日），end 直接抄（17:59 不减一天）。
    2. 下半（若出现）：`X HH:MM ~ Y HH:MM` → 显式起止，直接抄。
  - 按「」内祈愿名匹配（`merge_special_banners`），无需「·5星名」。「版本更新后」信号可纠正 `infer_banner_dates` 把「发布日 = 更新日」误判为下半的情况。
- `无神怜爱的雪国/冻土` = 限时剧情/探索奖励，**算常规活动**，打 `限时剧情奖励` / `限时探索奖励` 标签。
- `绮衣珍赏`（千星奇遇活动）= 常规活动。
- `幽境危战` = 高难关卡，每版本都有、名字不变 → 归 `高难挑战`，由 `find_challenge_announcements` 单独识别（已入 `CHALLENGE_KEYWORDS` 排除在常规活动外）；日期取正文 `〓活动时间〓` 的「整体活动时间 X~Y」，不参与 B站/版本推理。

**⚠️ 已知未处理的格式（会走日期闸丢弃，日志里以 `x` 报出）**：

- **三段式复合活动**：正文没有 `〓活动时间〓`，而是 `〓 子活动名 〓`（标记内**带空格**）分段，
  每段各写一行 `活动时间：…`。实例：`「虹旅藏金·耀星烁熠」`（含「凝取结晶双倍重置」/
  「佳礼来信·感恩答谢」/「耀星烁熠·累计登录」三段），日期写作 `2026/09/28 00:00起至7.1版本结束`。
  取哪一段的日期作为整条活动的起止没有明确答案（首段结束是「版本结束」、次段是显式日期），
  需人工决定策略。**已确认处置：不加解析分支，不记录，由人工补录**（编辑器 `main.py` 手动新增一条）。

**匹配**：米游社与 B站动态按 `「」` 括号内活动名匹配。⚠️ `七圣召唤` 是系统名、多个活动（热斗/铸境研炼）共用，**不参与 B站匹配**（其日期都在米游社正文里，避免串日期）。

## 八、颜色

- 每条活动的 `color` 根据**公告封面图主色**大致取一个（`fetch_post` 返回的 `images[0]`），再调亮成浅色。
- **必须浅色**：日历上是黑字，颜色太深看不清。做法：取主色色相，饱和度压到 ≤0.7、亮度提到 ~0.84（即与白色混成 pastel）。
- 取不到图 / 解析失败时用默认浅色兜底。

## 九、运行日志与风控

自动化维护是**无人值守**的，`logs/YYYY-MM-DD.log`（UTF-8，按天追加）是事后核查「那天到底干了什么」的唯一依据。每次运行开头带时间戳，内容包括：

```text
=== 2026-09-21 15:13:31 运行 ===
== 维护预告 == 7.1版本更新维护预告 → 2026-09-23 往冥府的安魂歌
== 正文抓取 == 成功 2 / 失败 0 / 跳过正文 18（已存在）
== 跳过（日期不完整）==
 x 「虹旅藏金·耀星烁熠」 ? ~ ?
共 0 新增 / 11 跳过 → 已写入
```

**判断本轮结果是否可信，先看「正文抓取」这一行**：

| 现象 | 含义 | 处置 |
|---|---|---|
| `失败 0` | 正常 | — |
| `失败 N（其中风控 1034: N）` | 米游社风控，本轮正文大面积缺失 | **别重跑**（会加重风控），等冷却后自然恢复；当天确有新活动则人工补录 |
| `失败 N` 但不含 1034 | 网络抖动 / 单条公告异常 | 下次运行自动补上 |

`retcode` 必须上报：风控的 `message` 是空的，只报 message 的话日志里只有「API 返回错误: 」，事后无法分辨原因。

**已落盘条目不抓正文（降风控的主要手段）**：风控的根因是请求数，而正文（`fetch_post`）是请求的大头。稳态下一次运行原本要抓 ~20 次正文，其中绝大多数是为了「确认某活动已经存在」——正文只用于取日期/描述/配图，都是**新增**才需要的东西。因此 `run_pipeline._needs_body` 会先用 `keys.find_duplicate` 对数据文件预筛，命中的条目**跳过正文抓取**。实测 20 次 → 2 次（1 条对不上键的版本大活动 + 1 次维护预告）。

设计上有三个要点，改动这块时别踩：

1. **判定复用 `apply_events` 的同名去重**（同一个 `keys.find_duplicate` + 同一份数据文件），所以不会比现有去重更激进——它跳过的，apply 本来也会跳过，不会因此丢新活动。
2. **命中的条目只跳过正文，不从列表里移除**。校准的权威来源来自 `merged`/`banners`（`_build_sources` 只读 `source` 与日期，不读正文），剪掉列表会连带丢掉卡池/版本大活动的校准来源。
3. **命中条目打 `_body_skipped` 标记**，它没日期是正常的，所以日期闸不再把它报成「日期不完整」——否则每天刷一屏，会淹掉真正的缺口。该标记是内部字段，`extracted_full.json` 走白名单导出，不会外泄。

因此日志里 `共 N 跳过` 会比以前小（已达日期的重复条目仍会走完流程，缺日期的被静默丢弃）；`跳过正文 M（已存在）` 这一项才是它们的去处，两者相加才是「本轮确认已存在的条目数」。

**已知待改进**：正文**按 `post_id` 本地缓存**。预筛已经消掉了稳态下的重复抓取，缓存的价值降到「同一天内多次运行不重复抓新条目」，优先级不如从前。

**未登录状态下的连带现象**：米游社网页是 SPA，正文由前端调同一个 `getPostFull` 渲染，接口回 1034 时页面直接显示 404 —— 所以「浏览器未登录看不了帖子」和「脚本抓不到正文」是**同一个原因**（同一个接口被风控），不是平台封禁。实测**登录后浏览器可正常查看**。

**⚠️ 但 cookie 不是确定的解**：本项目脚本在此前**未登录**的情况下成功抓取过大量正文，之后才开始被拦。所以 1034 更像**行为/频率触发的风控**（连续多次运行是主因），登录态只是提高信任等级、降低触发概率，而非「必须登录」。遇到风控**首选等冷却**，cookie 是复发时的缓解手段。真正治本的是上面那条「减少请求数」。

**设置 cookie**（与 B站 `SESSDATA` 同一套路，见记忆 `bili-sessdata-registry`）：

1. 浏览器登录米游社 → F12 → **网络 / Network** → 筛选 `getPostFull`（随便打开一个帖子详情即可产生请求）
2. 选中该请求 → **请求标头 / Request Headers** → 复制 `Cookie:` 后面的**整串**（不用挑字段名，直接整串拷最稳妥）
3. 设为环境变量（`setx` 写的正是代码读取的 `HKCU\Environment`）：
   ```bat
   setx MIYOUSHE_COOKIE "整串粘贴到这里"
   ```
4. 重新运行管线即可。`run_pipeline.py` 会先从注册表预读进 `os.environ`，已开着的终端/编辑器无需重启。

cookie 属凭据，**不要写进仓库、不要贴进对话**；未设置时该功能自动跳过，不影响运行。

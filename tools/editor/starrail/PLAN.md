# 星铁自动化维护 — 方案

> **状态**：方案已确认（2026-09-21），§6 的 4 处实现决策一并确认。
> 代码在 `tools/editor/starrail/`，§3 的验证项全部通过。
> 已实测的规则见 [RULES.md](RULES.md)，本文只讲**怎么做**。

## 1. Context

原神侧的管线（`genshin/pipeline.py` → `common/apply_events.py`）已经跑通，但全部逻辑是
按原神的公告格式写的。星铁的公告格式和规律都不一样，需要一套对应的实现。

原先以为「星铁很多经验不能直接迁移」——这话对，但**有一个关键源头一开始漏了**：
米游社的**版本更新说明**。它每版本开服当天发，是一份总纲，含版本名、本版起止、
**下版本日期**、高难四支的期名与日期。有了它：

- 版本周期不固定不再是问题（不用外推，直接读到下版本日期）
- 高难不再「无公告来源」（期名+日期都在里面）

于是星铁**全部类型都可自动化**，且比原神更少依赖推理。

**目标**：跑一次管线，新增活动/卡池/版本更新/前瞻/高难/大月卡自动落盘，
已有条目按权威来源校准——与原神同等程度的维护自动化。

## 2. 实施方案

### 2.1 模块划分

与原神**并列**的两条线，不是同一套逻辑的参数化：段落标记、卡池标题来源、版本节奏
都不同，硬塞进同一个函数只会变成一堆 if 分支。真正通用的走 `common/`。

```
tools/editor/
├── common/           两条管线共用
│   ├── yaml_io.py      数据文件读写
│   ├── keys.py         条目身份键 / 去重
│   ├── calibrate.py    权威来源校准（原神/星铁共用机制）
│   ├── extractor.py    米游社抓取 + 正文解析（按 game_id 参数化）
│   ├── bilibili.py     B站动态
│   ├── apply_events.py 新增落盘
│   └── colors.py       封面图取色
├── genshin/          原神管线
│   ├── pipeline.py     编排（原 run_pipeline.py）
│   ├── inference.py    周期性推理（星铁不用）
│   ├── RULES.md / PLAN.md
│   └── extracted_full.json
└── starrail/         星铁管线
    ├── rules.py        常量：抓取参数、排除词、段落名、颜色、标题格式
    ├── parse.py        纯函数解析层，不联网不读写文件
    ├── pipeline.py     编排：抓取 → 解析 → 校准 → 写 extracted_hsr.json
    ├── selftest.py     离线自检
    ├── fixtures/       真实公告夹具
    ├── RULES.md / PLAN.md
    └── extracted_hsr.json
```

`starrail/parse.py` 全部是纯函数，正确性由 `selftest.py` 用 `fixtures/` 里的真实公告断言
（当前 78 项全通过）——这样规则改动可以离线验证，不必反复联网。

### 2.2 `pipeline.py` 的 `run()` 顺序

1. `fetch_post_list(GAME, page_size=40)`，按 `post_id` 去重
2. 解析各来源；**`_needs_body` 预筛**（复用 `keys.find_duplicate`，已落盘的条目跳过正文抓取）
   ——米游社正文才有风控，这个预筛是稳态请求数的主控
3. 版本大活动：正文含「X.Y版本期间」→ 起止 = `[版本更新日, 下版本日期 − 1]`
4. 高难：从版本更新说明直接产出；异相仲裁只给期名，起止按版本期间补
5. B站：`fetch_dynamics(1340190821, limit=80)` → 前瞻直播 + 上线日期
6. 版本更新占位：**只用已知来源**——版本更新说明的 `start_date` / `next_version_date`、
   B站上线动态、米游社更新预告；三者都没有就不产出（不做周期外推，星铁周期不固定）。
   只有日期、还不知道版本名时标 `待确认版本`，等更新预告/B站上线动态由 calibrate 补全
7. 校准 `calibrate(events, sources)`；有变更直接落盘
8. 日期闸 → 取色 → 写 `starrail/extracted_hsr.json` → 交 `apply_events.main`

### 2.3 通用层的小改动（加法式，原神行为不变）

| 文件 | 改动 |
|---|---|
| `common/yaml_io.py` | 抽出 `GAME_ID_PREFIX` / `GAME_URL_PATH`，`generate_event_id` 改用前者 |
| `common/apply_events.py` | `auto_id(...)` 与 `main(...)` 加 `game_id` 参数；`source_url` 用 `GAME_URL_PATH` 拼；产物文件名变成参数 |
| `common/calibrate.py` | `sources_from(..., game_name="原神")` —— 只把写死的「原神」提成参数；`calibrate()` 本身不动 |
| `maintain.py` | 循环跑两个游戏，日志按游戏分节 |

**不改**：`common/extractor.py`、`common/bilibili.py`、`genshin/inference.py`、
`gui.py`、`main.py` 的逻辑（只跟着模块搬迁改了 import）。

> ⚠️ `maintain.py` 跑两个游戏会让每日请求翻倍，米游社风控（retcode 1034）是已知痛点。
> 但预筛把稳态正文请求压到很低，列表接口不受风控影响，增量可接受。
> 若实测风控变频繁，退路是拆成两个入口各自调度。

### 2.4 数据订正（`data/events/honkai-star-rail.yaml`）

1. **4.6 版本更新 `2026-09-30` → `2026-09-28`** —— 三条独立证据：B站前瞻「4.6 将于
   2026年9月28日上线」、4.5 更新说明「持续时间为 … - 2026/09/28 06:00」、
   无名勋礼与超限大奖赛都结束于 `2026/09/28 03:59`
2. **版本更新旧条目规范化** —— `hsr-版本停服更新` 这个 id 被 4.4 与 4.5 两条共用
   （id 是前端 React key），且 4.4 标题是光杆的 `4.4版本停服更新`；改为各自唯一 id
3. **两条常规活动标题改写** → `「位面分裂」`、`「花藏繁生」`（不改的话下次跑会被当成新活动插重复）
4. **两条整版活动类型改 `版本大活动`** —— `「幻造：圣杯战争」`、`「反贪『砖』家」`
5. **日期口径订正三条** —— `末日幻影·兵锋骑士` end `8/31` → `8/30`；
   `末日幻影·仙客天狼` start `9/01` → `8/31`；`「位面分裂」` end `8/10` → `8/09`
6. **忘却之庭两条改用官方写法** —— `忘却之庭·学院怪谈` → `混沌回忆·学院怪谈`；
   `忘却之庭·扫除风暴` → `混沌回忆·扫除风暴`（含 id）

## 3. 验证方式

**离线核验（不碰网络）**

1. `python starrail/selftest.py` —— 用 fixtures 逐条断言：卡池标题与数据文件**逐字一致**；
   高难各条的期名+日期与订正后一致；`parse_version_notes("4.5…")["next_version_date"] == "2026-09-28"`
2. `keys.find_duplicate` 交叉检查：解析出的条目对现有数据逐条跑一遍，
   **除已知要新增的（`虚构叙事·立界开篇`、`4.5版本「无名勋礼」`、`「镇伏『贪饕』，汇聚愿力」`），
   其余应全部命中已有条目**
   > 落盘后自检清单同步收窄（`selftest.KNOWN_NEW` 去掉前两条）：它们现在**应该**命中，
   > 留着反而下一轮误报。仍不命中只剩 `「镇伏『贪饕』，汇聚愿力」`——它终点未知、本就没落盘。

**端到端（2026-09-21 已跑两轮，见 [../genshin/PLAN.md](../genshin/PLAN.md) §4）**

1. `python maintain.py` 跑双游戏 → ✅ 两节齐全，抓取**失败 0、风控 0**
2. 星铁 4 条落盘（22 → 26 条）→ ✅ 其中一条是原先手工录入漏掉的 4.4 卡池
3. 原神侧逐字节未变（md5 前后一致）→ ✅ 模块搬迁的回归底线达成
4. `npm run build` → ✅ 通过（tsc + vite，117 modules，1.64s）
5. 浏览器确认星铁日历渲染正常，暗色/亮色都看一遍 → ✅ 渲染正常，内容与版本更新说明一致
6. 点一条 `source_url` 确认 `/sr/` 路径 → ✅ 打开即星铁 4.5 版本更新说明
   （URL 形如 `https://www.miyoushe.com/sr/article/77754792`）

> 幂等的措辞已按实测更正：第二轮是「0 新增」但会多打一个 `calibrated` 标记，
> 不是字节级不变。原因与结论见 [../genshin/RULES.md](../genshin/RULES.md) §6.4。

## 4. 遗留 / 不做

- **卡池复刻池（铭心之萃）**：4.4 其二里返场池与首发池时间不同，规则已能正确拆成两条。
  若将来出现「同一公告内三个以上时间段」，需要再看实际文本。
- **登录福利类**（巡星之礼、命运契约等）：版本更新说明里提到了，但多数不给明确起止，不收录。
- **原神侧的任何重构**：不动。

## 5. 已定口径

- **版本大活动终点未知时不猜，等它自己的版本更新说明**（2026-09-21 定）。
  4.6 的两条（`「镇伏『贪饕』，汇聚愿力」`、`「星际幻宠」`）只知道 start（2026-09-28），
  end 要等 4.6 开服当天那份说明。公告还留在抓取窗口里，届时自然被收进来。
  宁可日历上晚几天出现，也不落一段错日期。
- **`source_url` 的路径**：用 `/sr/article/{id}`（原神是 `/ys/`）。两者都返回 200
  （SPA 不区分），无法用状态码判定。**2026-09-21 人工确认：打开即星铁 4.5 版本更新说明**，
  路径正确。

## 6. 实现决策（2026-09-21 已确认）

写代码时为了跑通实测数据做了 4 处超出本方案原文的决定，均已确认保留：

| # | 决策 | 为什么 |
|---|---|---|
| A | `ACTIVITY_SECTION = r"[▌■]\s*(活动时间\|限时活动期\|开启时间)"`，收 `■` | `「星际幻宠」乐园` 标成 `■活动时间`，不收就永远收不进来 |
| B | `EXCLUDE` 加 3 个词：`任务说明` / `赛季扩充` / `权益升级` | 这三种公告没有活动时间段，每轮白抓正文又永远落不了盘（无日期被闸掉） |
| C | `CALIBRATED_TYPES` 加 `高难挑战` | 否则版本更新说明里那份权威高难日期白拿（对原神是空转，原神的高难无公告） |
| D | 公告列表按 `post_id` 去重、卡池按标题去重 | 实测同一篇公告在列表里出现两次；同一期卡池在「其一/其二」各出现一次（姬子•启行整版都在池） |

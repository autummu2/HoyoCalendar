## 1. 已完成的功能

### 1.1 八类活动的自动化

| 类型 | 来源 | 校准依据 |
|---|---|---|
| 版本更新 | 版本更新说明 / 更新预告 / B站上线动态 | 米游社维护预告 > B站前瞻公告 |
| 前瞻直播 | B站动态（「正式播出」） | B站前瞻公告 |
| 卡池 | 标题 `X.Y版本活动跃迁`，5 星名**从正文拼** | —（标题与数据文件逐字一致） |
| 高难挑战（四支） | 版本更新说明的 `■玩法` 段 | 米游社版本更新说明 |
| 常规活动 / 版本大活动 | 活动自己的公告（§1.2 也可来自总纲） | — |
| 大月卡 | 标题含 `无名勋礼` | — |
| 登录福利 | 总纲里没有 `活动时间：` 的那条（§1.4） | — |

**关键前提**：米游社的**版本更新说明**是一份总纲，每版本开服当天发，含版本名、本版起止、
**下版本日期**、高难四支期名与日期。有了它，星铁的**全部类型都可自动化**，且比原神更少
依赖推理——星铁版本周期不固定（4.4→4.5 = 42 天，4.5→4.6 = 33 天），原神那套周期性外推
在这里是错的，所以星铁**不做周期性推理**。

### 1.2 总纲优先 + 订正通道（2026-09-21）

活动落盘的时点由**最早给出日期的那份公告**决定。总纲的 `X、全新活动` 段逐条列出本版活动名
与 `活动时间：`，实测**比活动自己的公告早 15 天**（4.5 总纲 08-26 发布，`「方寸大冒险」` 的
公告 09-10 才发），所以这一段直接收进来。

代价是总纲给不出**类型、配图、正文描述**——落盘时用默认类型 + `keys.PENDING_FIELD` 标记，
等它自己的公告发出来后由 `calibrate.correct_from_candidates` 补齐并清掉标记。

**只收当前版本的那一份总纲**（2026-09-21 定）：窗口里通常还留着上一版的总纲，而从它产候选
有实测风险——4.4 总纲把那条联动活动写作 `■命运/银河铁道之夜`，公告与数据文件里都叫
`「幻造：圣杯战争」`（同一活动、两个名字），按标题去重认不出来，会插一条**重复**。

标记机制与绝区零共用一套（设计说明见 [../zenless/PLAN.md](../zenless/PLAN.md) §1.2）：
`pending` 是预筛的**一票否决**（`keys.likely_recorded` 见到就不跳过正文），所以待补全的条目
一定会被抓一次正文；补全后标记清掉，下一轮不再重抓。

### 1.3 一帖多活动（2026-09-22）

一篇活动公告可能挂着**多条**活动。实测 `「幻造：圣杯战争」活动说明`（post 76891951）里除
主体还有两块：`「命运契约•再启」`（`■活动时间 2026/07/24 12:00 - 4.6版本结束前`）与
`「命运赠礼」`（`■活动时间 4.4版本期间`）。原来只读**第一个** `活动时间` 段，这两条永远
看不见——而它们的名字**不在公告列表里**，没有任何别的渠道能发现。

- `parse.parse_activity_bodies(text, name)` 按 `▌「X」活动说明` 切块，各块只认自己那段的
  `活动时间`；一帖一活动的公告整篇就是首块，名字取 subject
- **标题取各块自己的活动名**（`「命运赠礼」`），不拼「主体名 + 块名」——数据文件与公告里
  都是这么叫的，标题又是去重主键
- 相对终点 `X.Y版本结束前` 按版本周期表补；表里没有那一版就留空（不猜）

### 1.4 登录福利（2026-09-22）

`巡星之礼` 每版本都有，总纲里**没有 `活动时间：`**（写的是「活动期间，每日登录…」），而它
从来没有自己的公告——不就地收，就永远进不了日历。

判据是**条目本文里没有 `活动时间：`**，不是「日期解不出来」——后者必须分开：`命运契约•再启`
有 `活动时间：`（只是终点写成相对版本号），它的时段不等于版本期间，套上会落一段错日期。
措辞（`rules.LOGIN_KEYWORDS`）作第二道确认。时段取**版本期间**（起止都是总纲自己给的相邻
更新日，不是外推）。这条候选**不打 `pending`**：没有公告可等，打了没人清，会永久留在数据文件里。

> 已知取舍：`巡星之礼` 的真实领取窗口是 7 天签到（大约版本前半段），这里按整版显示。

### 1.5 正文缓存 + 审读闸门（2026-09-22）

**米游社只有正文接口有风控**（`retcode 1034`），所以正文抓取次数是关键指标。三道措施：

| 措施 | 作用 |
|---|---|
| `_needs_body` 预筛 | 已落盘的条目跳过正文（复用 `keys.find_duplicate` + `likely_recorded`，不会比 `apply_events` 的去重更激进） |
| `common/body_cache.py` 正文缓存 | 按 `post_id` 存正文，TTL 14 天。版本更新说明、卡池这些**每轮都要读**的公告稳态降到 0 请求 |
| **审读闸门**（只给活动公告） | 一帖多活动要求读正文，但**只读到「还有块在等」为止** |

审读闸门的判据是**派生的**（「这篇还有没啃下来的块」），不需要任何名单：

| 上一轮的结果（`audited.json` 的 `waiting`） | 这一轮 |
|---|---|
| 还有块在等版本周期表（如 `幻造` 里埋的 `命运契约•再启` 等 4.6 的止） | 再读一遍；那一版日期一确认就落盘，随后自动转成跳过 |
| 全部块都落盘了 | **跳过，连 TTL 都不等**——和原神同一套跳过逻辑 |
| 一条都没解析出来（格式变了 / 残页） | 记 `waiting`，下轮再看 |

为什么缓存用 TTL 而不是永久：公告会被**事后编辑**（补录活动、订正日期——订正机制就是为这种
编辑准备的），14 天既挡住绝大部分重复请求，又让编辑后的版本最多两周内被读回来。

### 1.6 版本周期表：由条目推，不从正文重算（2026-09-22 改口径）

所有相对写法（`X.Y版本期间` / `X.Y版本结束前` / 高难「异相仲裁」的起止）都查这张
`{版本号: (起, 止)}` 表。原口径是「窗口里**每份**版本更新说明都读，现算表」；改后**由版本
更新条目推**——条目标题带版本号，落盘并校准后版本更新日就是权威值，止 = 下一条的日期 − 1 天。
口径与原神 `inference.extract_version_dates` 一致。

改完的三点差别：**旧版本的说明不再读**（`_collect_notes` 只取最新那份）、**不再受 40 条窗口
限制**（`命运赠礼` 写的 `4.4版本期间` 可以指向很早的版本）、`_version_period` 随之删除
（「版本期间」的算法只剩一处）。

两条**假定**：表内相邻即实际相邻（没落盘的版本不会出现在表里，也就不会被引用）；最后一条的
止是 `None`——星铁**不做 42 天那种兜底外推**，拿不到止的条目被日期闸丢掉，不落错日期。

### 1.7 身份改造：双倍掉落类不再静默丢数据（2026-09-21）

去重主键见 [RULES.md](RULES.md) §4.2。这里记的是**为什么加 `DATED_KEYED_PREFIXES` 这个例外**
——起因是 §4 里「2026-09-21 — 身份改造」那条静默漏数据。

### 1.8 权威校准

`common/calibrate.py`（与原神共用机制）拿权威来源核对已落盘条目，只改值 + 打 `calibrated`
标记，不新增。星铁的权威来源见 [RULES.md](RULES.md) §4.4。高难那一支是**星铁独有**：期名与
日期都写在版本更新说明里（对原神是空转，原神的高难无公告）。

### 1.9 模块划分

与原神**并列**的两条线，不是同一套逻辑的参数化：段落标记、卡池标题来源、版本节奏都不同，
硬塞进同一个函数只会变成一堆 if。真正通用的走 `common/`。

```text
tools/editor/
├── common/           三条管线共用（body_cache.py 目前只有星铁/绝区零用）
├── genshin/          原神管线（inference.py 那套周期性推理星铁不用）
└── starrail/
    ├── rules.py      常量：抓取参数、排除词、段落名、颜色、标题格式
    ├── parse.py      纯函数解析层，不联网不读写文件
    ├── pipeline.py   编排：抓取 → 解析 → 订正 → 校准 → 写 extracted_hsr.json
    ├── selftest.py   离线自检（144 项）
    ├── fixtures/     真实公告夹具
    ├── RULES.md / PLAN.md
    └── extracted_hsr.json
```

`parse.py` 全是纯函数，正确性由 `selftest.py` 用 `fixtures/` 的真实公告断言——规则改动可以
离线验证，不必反复联网。

**通用层的加法式改动**（原神行为不变）：`yaml_io` 抽出 `GAME_ID_PREFIX` / `GAME_URL_PATH`；
`apply_events.auto_id` / `main` 加 `game_id` 参数；`calibrate.sources_from` 把写死的「原神」
提成参数；`maintain.py` 循环跑三个游戏。**不改** `extractor.py` / `bilibili.py` /
`genshin/inference.py` / `gui.py` / `main.py`。

## 3. 验证方式

### 3.1 离线核验（不碰网络）

1. `python starrail/selftest.py` —— 用 `fixtures/` 逐条断言：卡池标题与数据文件**逐字一致**；
   高难各条的期名+日期与订正后一致；`parse_version_notes("4.5…")["next_version_date"] ==
   "2026-09-28"`；一帖多活动三块的（名字、时段、相对终点）；登录福利的时段与类型；正文缓存的
   TTL 语义与那道 `audit` 闸门（含 `waiting` 的两端）；版本周期表由条目推（含「候选覆盖旧日期」
   「没有版本号的标题不进表」）—— **144 项**（2026-09-22）
2. `keys.find_duplicate` 交叉检查：解析出的条目对现有数据逐条跑一遍，除已知要新增的之外
   其余应全部命中已有条目
   > 「不命中」的判据后来换成了**日期不齐**（管线日期闸会丢掉这类条目），不再用手写名单。
   > 起初的例外名单 `KNOWN_NEW` 已删除：名单会过期，过期了还留着就会把真正的标题规则回归
   > 盖住。**这条自检加强当场炸出一条静默漏数据**，见 §4 的「2026-09-21 — 身份改造」。

### 3.2 端到端

```bash
python maintain.py            # 三条管线，或 python starrail/pipeline.py 单跑
npm run build                 # 只改 tools/editor/ 下的 Python 时不必跑
```

每轮的判读顺序：**请求数**（`== 正文抓取 ==` 行，含 1034 别重跑）→ **新增条数** →
**`== 跳过（日期不完整）==`**（缺口可见性的主要来源）→ 数据文件 md5（幂等核对）。

三轮实盘的完整记录见 §4，此处不重复。

> 幂等的措辞已按实测更正：第二轮是「0 新增」但会多打一个 `calibrated` 标记，不是字节级不变。
> 原因与结论见 [../genshin/RULES.md](../genshin/RULES.md) §4.4。

## 4. 开发记录

按日期倒序归档：每条记**起因 / 改了什么 / 实测 / 经验**。「经验」是当时踩出来、之后一直适用的
结论；仍然生效的决策另在 §5、§6 汇总。

### 2026-09-24 — 一轮实盘：`EXCLUDE` 补 `更新说明`

**起因**：跑一轮实盘（9/23 发了一批公告）时，日志里那条「日期不完整」的 `x` 里有
`「货币战争•零和博弈」更新说明 V4.6` —— 9/21 补的 `赛季扩充` 是按 4.4 那期标题（`…赛季
扩充说明 V4.4`）加的，这期改名成「更新说明」，名单就拦不住了。

**改了什么**：`rules.EXCLUDE` 加 `更新说明`。它顺带覆盖了名单里原有的 `版本更新说明`。

**实测**：候选集合新旧对比，**只少了「货币战争•零和博弈」一条**；版本族 9 条公告
（2 条版本更新说明 / 2 条更新预告 / 4 条活动跃迁 / 1 条无名勋礼）的处置全部不变。
原因是 `EXCLUDE` 只在 `parse.is_activity` 一处被读，而版本族在那之前就由
`is_version_notes` / `is_update_preview` / `is_banner` 判掉了，收集它们的 `find_*`
根本不看 `EXCLUDE`（见 [RULES.md](RULES.md) §2.2 的 ⚠️）。

**经验**：**按标题措辞维护的排除名单会随公告改名叫停摆**。`赛季扩充` → `更新说明` 是
同一类公告的两种叫法，名单拦不住新的那种，症状是「每轮白抓一次正文、又永远落不了盘」——
**这类症状（而不是「数据错了」）才该触发补词**。补词时唯一要确认的是「这个词会不会
把真正要收的公告一起挡掉」，而这里的答案是结构性的：EXCLUDE 只影响活动分类那一条路。

### 2026-09-23 — 文档全面整理

**起因**：RULES 与 PLAN 是随开发一处处追加出来的，规则散在「实施方案」的叙述里，新读者
（包括几个月后的自己）要读完 455 行才知道某类活动到底怎么跑。

**改了什么**：两份文档重写。RULES 只讲**管线运行逻辑**（分类方法 → 每类活动一张
mermaid 流程图 → 全局规则），PLAN 只讲**做了什么 / 还差什么 / 当时怎么想的**，把过程性内容
收进本节。**代码未动。**

**经验**：

- **规则文档按「读者的问题」组织，不按「开发的顺序」**：读者先问「这条公告算哪一类」，再问

  图语法），2026-09-24 确认是 markdown-mermaid 预览插件与其它插件的冲突，插件侧修好后不再

### 2026-09-22 — 活动公告的审读闸门

**起因**：一帖多活动要求「已落盘的活动公告也读正文」（§1.3），但这等于把活动公告变回每轮
必读，把前一天刚降下来的请求数又推回去。

**改了什么**：`body_cache` 的 `audited.json` 从「裸日期」扩成 `{date, waiting}`，
`archive_state` 派生出 `audit_state`；`pipeline._build_activities` 逐块算日期后回写
`waiting`。旧格式（裸日期字符串）一律当 `waiting=True`——多读一次自纠，不会把「还有块在等
版本周期表」的那篇误判成已经啃干净。

**实测**（同一台机连跑两轮，给 `_fetch_text` 打点）：

| | 活动公告 | 卡池 | 版本更新说明 | 更新预告 | 合计 |
|---|---|---|---|---|---|
| 第一轮 | 10 | 4 | 1 | 1 | 16 |
| 第二轮 | **3** | 4 | 1 | 1 | **9** |

全部缓存命中；`data/events/honkai-star-rail.yaml` md5 两轮都是 `7a5cd4c3…`（0 新增）。
第一轮仍是 10 篇是 `audited.json` 旧格式的一次性迁移代价，**不是常态**。

**差集核对**（闸门开 / 强制 `audit_state` 返回 `None` 各跑一轮 `run()`）：被跳过的 7 篇少产出的
候选——`异器盈界`、`方寸大冒险`、`位面分裂` ×2、`超限：狂飙大奖赛`、`花藏繁生`、`反贪『砖』家`
——**逐条都能在数据文件里按标题找到**，没有孤儿。

**经验**：

- **「多久之后重读一次」和「还需不需要读」是两个问题**。TTL 回答前者，判据回答后者；缓存
  该按 TTL 走（公告会被事后编辑），而审读该按状态走（这块啃下来没有）。混在一起就会为了
  等一条四年后才有的数据而每两周白读一遍
- **判据要派生，不建名单**：`waiting` 是「这篇还有没啃下来的块」算出来的，不是一张「需要
  重读的公告」清单——名单会过期，过期了还留着就会把真正的回归盖住
- `_needs_body` 的 `audit` 只交给活动公告：大月卡 / 卡池的正文里没有「活动」可漏，给它们
  开这道门只是白读
- 自检要**钉住闸门的两端**（`test_activity_audit_waiting` 拿 `幻造` 那篇一帖三活动的真身：
  4.6 只有起无止 → `waiting`；补上 4.6 的止 → 块全落盘），只钉一端的话闸门失效也不会报警

### 2026-09-22 — 版本周期表改由条目推

**起因**：`_collect_versions` 让窗口里**每份**版本更新说明都读一遍，只为了现算一张
`{版本号: (起, 止)}` 表——而这张表本来就是重复推导。

**改了什么**：`_version_table(entries)` 由版本更新条目（数据文件 + 本轮候选）推，止 = 下一条
的日期 − 1 天；`_collect_notes` 只取最新那一份；`_version_period` 删除（异相仲裁改查同一张表）。

**实测**：`绝区零 → 星铁` 两轮连跑，两轮都 **0 新增**，数据文件 md5 与改口径前**完全相同**；
表本身 `4.4 07-15 ~ 08-25，4.5 08-26 ~ 09-27` 与原算法**逐字一致**，另多出 `4.6 09-28 ~ None`
（旧表里没有 4.6：它只认窗口里那两份说明）；缓存命中 17 → **16**，少的那篇正是 4.4 的说明。
自检 137/137。

**经验**：

- **先问「这个中间产物能不能从已落盘的权威值推出来」**。版本更新日一经校准就是权威值，
  从它推表既准确又不受抓取窗口长度限制——而按窗口现算，等于把「4.4版本期间」这类写法的
  正确性押在「4.4 的说明还留在 40 条窗口里」
- 改口径后**必须核对数据文件 md5**：这次是零影响，所以可以放心合并；如果 md5 变了就得逐条
  解释为什么变，不能只看「0 新增」

### 2026-09-22 — 一帖多活动 + 登录福利 + 正文缓存

**起因**：一帖多活动是**漏数据**（被埋的活动名字不在公告列表里，没有别的渠道能发现）；
登录福利是**永远收不进来**（没有自己的公告）；正文缓存是**风控**（正文请求数是主因）。

**改了什么**：`parse.parse_activity_bodies` 分块解析 + `_activity_dates` 查全部版本的周期表；
`parse_version_activities` 认「没有 `活动时间：` + 登录措辞」→ 登录福利；新增
`common/body_cache.py`。

**实测**：`绝区零 → 星铁` 两轮连跑（`logs/2026-09-22.log`）——第一轮星铁 2 新增
（`「命运赠礼」` 来自正文分块、`「巡星之礼」` 来自总纲），绝区零 0 新增；第二轮**两游戏都
0 新增、0 请求**（全部缓存命中），数据文件 md5 与第一轮一致。`「命运契约•再启」` 出现在
「跳过（日期不完整）」里（`2026-07-24 ~ ?`）——缺口可见，不是静默丢弃。自检 132/132、
绝区零 255/255、`npm run build` 通过。

**经验**：

- **「公告列表里有」不是发现新活动的充分条件**：一帖多活动意味着真正的活动集合是「所有公告
  的正文里提过的活动名」，前者只是后者的子集。这个盲区不读正文就永远看不见
- **相对写法的终点要能留空**：`4.6版本结束前` 解不出来时留空、由日期闸丢掉、并在日志里以
  `x` 报出——**报出**是关键，静默丢弃和「本来就该丢掉」在日志上必须能分开
- **缓存的 TTL 要跟「数据会不会变」对齐**，不是跟「多久跑一次」对齐。公告会被事后编辑，
  所以是 14 天而不是永久

### 2026-09-21 — 身份改造：双倍掉落类不再静默丢数据

**起因**：把 §3.1 的例外名单换成日期判据时，顺手给大月卡和 3 条活动补上了日期核对
（78 → 85 项）——**多出来的核对当场抓到一条静默漏数据**：9 月那期 `「位面分裂」`（9/07~9/20）
公告抓到了、日期也解析对了，**却没进日历**——去重主键只认标题，7 月那期（7/27~8/09）已经
占了同一个 `「位面分裂」`，`apply_events` 就当重复条目跳过了。不报错、日志无异常，只是日历上
少一条。

**改了什么**：把 `「位面分裂」`/`「花藏繁生」`/`「异器盈界」` 加进 `common/keys.py` 的
`DATED_KEYED_PREFIXES`，主键带上开始日期。原神的深境螺旋/幻想真境剧诗本来就走这条，是为
**同一类**问题准备的机制，不是新开的口子。

**实测**：

| 检查项 | 结果 |
|---|---|
| 主键改动的爆炸半径 | 原神 50 条**一条未变**；星铁只动了那 3 条 |
| 原神数据文件 md5 | `8a6a2aad…` 前后一致 |
| 管线跑一轮 | 星铁 26 → 27，9 月那期落盘；抓取失败 0、风控 0 |
| 自检 | 85/85 |
| 离线幂等（产物对更新后的数据重跑去重） | 0 新增 |

**经验**：

- **静默丢弃比报错危险得多**。这条数据「抓到了、解析对了、就是没进日历」，全链路无异常——
  只有「自检主动拿解析结果对数据文件核对」才炸得出来。所以自检的价值不在断言函数返回值，
  而在**用真实数据跑一遍全链路**
- **例外名单是负资产**（见 §3.1 的 `KNOWN_NEW` 注释）：名单会过期，过期了还留着就会把真正的
  规则回归盖住。判据一律派生
- 代价如实记下：这几条的日期在正文里，预筛拿不到日期就没法提前命中，所以它们每轮多抓一次
  正文（1~3 条）——换来的是不再静默丢数据

  这类改动要连 id 一起看

  加高难、列表/卡池去重）当时就确认保留，见 §6

## 5. 已定口径

仍然生效、且**改代码前必须先看**的结论。凡与代码注释或 [RULES.md](RULES.md) 冲突的，
以本节为准（本节是决策，RULES 是现状描述）。

- **版本大活动终点未知时不猜，等它自己的版本更新说明**（2026-09-21 定）。宁可日历上晚几天
  出现，也不落一段错日期
- **`run()` 的第 8~11 步顺序是硬约束**（三条，绝区零同此）：
  1. **日期闸 → 取色 → 订正**：取色必须在**日期闸之后**（否则给马上要被丢掉的条目白下载
     封面图，`pastel_from_url` 是真网络请求），又必须在**订正之前**（订正补的「配色」正是
     取色的产物）
  2. **订正 → 校准**，两个理由各缺一不可：① 两者都写 `events`，校准读的是订正后的结果；
     ② 版本大活动的**主键含类型**，类型改对了校准才查得到权威来源
  3. 总纲候选与公告候选**按身份去重、留先出现的公告那条**（它有真类型与描述，总纲那条只有
     默认类型）
- **只收当前版本的总纲**（2026-09-21 定，理由见 §1.2）
- **一帖多活动：标题取各块自己的活动名**（2026-09-22 定）——不拼「主体名 + 块名」
- **已落盘的活动公告按「还有没有块在等」再审，不按 TTL 重审**（2026-09-22 定，当日改过一次
  口径）。判据派生，不需要名单；代价是 `audited.json` 旧格式那一轮会多读一次自纠
- **版本周期表由已确认的版本更新条目推，不从说明正文重算**（2026-09-22 定）
- **`source_url` 的路径用 `/sr/article/{id}`**（原神是 `/ys/`）。两者都返回 200（SPA 不区分），
  无法用状态码判定——**2026-09-21 人工确认**：打开即星铁 4.5 版本更新说明
